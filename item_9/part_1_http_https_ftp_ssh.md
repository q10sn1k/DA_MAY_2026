# DNS, HTTP, HTTPS, FTP, SSH и SFTP: основы сетевого взаимодействия с примерами на Python

## Для чего нужен этот материал

Программы редко работают полностью изолированно. Браузер получает страницу с сайта, аналитический скрипт загружает файл, приложение обращается к серверу, администратор подключается к удалённой машине, а информационные системы передают данные друг другу.

Во всех этих случаях происходит **сетевое взаимодействие**: одна программа отправляет сообщение, другая принимает его, обрабатывает и возвращает результат.

В этом материале рассматриваются пять базовых семейств технологий:

- **DNS** — преобразование доменных имён в адреса и получение служебных записей;
- **HTTP** — обмен веб-страницами, текстом, файлами и данными между клиентом и сервером;
- **HTTPS** — HTTP через защищённое соединение;
- **FTP и FTPS** — передача файлов между компьютерами;
- **SSH и SFTP** — защищённое удалённое управление сервером и передача файлов через SSH.

Основной акцент сделан на DNS, HTTP и HTTPS: DNS помогает найти сетевой адрес, а HTTP/HTTPS обеспечивают обмен веб-запросами и ответами. Именно эта связка лежит в основе обращения к сайтам и REST API. FTP, SSH и SFTP рассматриваются как отдельные рабочие инструменты, которые решают другие задачи.

После изучения материала вы сможете:

1. объяснить, что такое клиент и сервер;
2. прочитать структуру URL;
3. объяснить работу DNS, кэша и основных типов записей;
4. отличить HTTP от HTTPS;
5. понять назначение FTP, FTPS, SSH и SFTP;
6. выполнить простой HTTP-запрос из Python;
7. скачать файл по HTTPS;
8. понять структуру Python-кода для FTP, SSH и SFTP;
9. распознавать распространённые сетевые ошибки;
10. соблюдать базовые требования безопасности.

> Все примеры с удалёнными FTP-, SSH- и SFTP-серверами являются шаблонами. Для их запуска необходимы реальный адрес сервера, разрешённая учётная запись и доступ, предоставленный владельцем системы.

# 1. Как две программы обмениваются данными

## 1.1. Клиент и сервер

В простейшей сетевой модели участвуют две стороны:

- **клиент** — программа, которая начинает взаимодействие и отправляет запрос;
- **сервер** — программа, которая ожидает запросы, обрабатывает их и возвращает ответы.

Примеры клиентов:

- браузер;
- мобильное приложение;
- Python-скрипт;
- программа для передачи файлов;
- SSH-клиент;
- другая информационная система.

Примеры серверов:

- веб-сервер сайта;
- файловый сервер;
- сервер базы данных;
- сервер приложений;
- удалённая Linux-машина;
- сервер API.

Упрощённая схема:

```text
клиент
  |
  | запрос
  v
сервер
  |
  | ответ
  v
клиент
```

Например, браузер отправляет серверу запрос: «Верни главную страницу». Сервер находит нужный ресурс и отправляет HTML-документ. Браузер получает документ и показывает его пользователю.

## 1.2. Протокол

**Протокол** — это набор правил, по которым две стороны обмениваются сообщениями.

Протокол определяет:

- как установить соединение;
- как выглядит запрос;
- как выглядит ответ;
- какие команды допустимы;
- как передаются данные;
- как сообщается об ошибке;
- как завершается соединение.

Простая аналогия: протокол похож на правила деловой переписки. Если одна сторона отправляет сообщение в понятном формате, другая сторона может его правильно прочитать и обработать.

HTTP, FTP и SSH являются разными протоколами и решают разные задачи.

## 1.3. Адрес сервера

Чтобы клиент мог обратиться к серверу, ему нужен адрес.

В сетевом взаимодействии встречаются:

- **IP-адрес** — числовой адрес устройства в сети;
- **доменное имя** — удобное имя, например `example.com`;
- **порт** — числовой номер сетевой службы на сервере;
- **протокол** — правило взаимодействия, например HTTPS или SSH.

Пример:

```text
https://example.com:443/catalog
```

Здесь:

- `https` — протокол;
- `example.com` — доменное имя;
- `443` — порт;
- `/catalog` — путь к ресурсу.

## 1.4. Что такое порт

На одном сервере может работать несколько сетевых служб. Порт помогает понять, к какой именно службе обращается клиент.

Часто используются следующие порты:

| Технология | Типичный порт | Назначение |
|---|---:|---|
| HTTP | 80 | веб-соединение без TLS-защиты |
| HTTPS | 443 | защищённое веб-соединение |
| FTP | 21 | управляющее FTP-соединение |
| SSH | 22 | защищённое удалённое подключение |
| SFTP | 22 | передача файлов внутри SSH-соединения |

Эти значения являются стандартными значениями по умолчанию. Администратор может настроить службу на другом порту.

Если в URL порт не указан, клиент обычно использует стандартный порт выбранной схемы. Например, для `https://example.com` обычно используется порт 443.

# 2. URL: адрес ресурса

## 2.1. Что такое URL

**URL** — адрес ресурса в сети.

Пример:

```text
https://shop.example.com:443/products?category=books&page=2#results
```

Разберём его на части:

| Часть | Значение | Смысл |
|---|---|---|
| схема | `https` | по какому протоколу обращаться |
| хост | `shop.example.com` | к какому серверу обращаться |
| порт | `443` | к какой службе сервера обращаться |
| путь | `/products` | какой ресурс запрашивается |
| query string | `category=books&page=2` | дополнительные параметры запроса |
| fragment | `results` | локальная ссылка внутри документа |

## 2.2. Разбор URL через Python

Для разбора URL можно использовать модуль `urllib.parse`, который входит в стандартную библиотеку Python.

```python
from urllib.parse import urlparse  # Импортируем функцию urlparse для разбора URL на отдельные части.

url = "https://shop.example.com:443/products?category=books&page=2#results"  # Сохраняем пример URL в переменную.
parsed_url = urlparse(url)  # Разбираем URL и получаем объект с его компонентами.

print("Схема:", parsed_url.scheme)  # Выводим протокол, указанный в URL.
print("Хост:", parsed_url.hostname)  # Выводим доменное имя сервера.
print("Порт:", parsed_url.port)  # Выводим явно указанный номер порта.
print("Путь:", parsed_url.path)  # Выводим путь к ресурсу на сервере.
print("Параметры:", parsed_url.query)  # Выводим строку параметров после знака вопроса.
print("Фрагмент:", parsed_url.fragment)  # Выводим часть URL после символа решётки.
```

Ожидаемый смысл результата:

```text
Схема: https
Хост: shop.example.com
Порт: 443
Путь: /products
Параметры: category=books&page=2
Фрагмент: results
```

## 2.3. Доменное имя и DNS

Человек запоминает имя `example.com`, но сетевое соединение устанавливается с IP-адресом. Система DNS помогает преобразовать доменное имя в IP-адрес.

Упрощённо:

```text
example.com
    ↓ DNS
192.0.2.10
    ↓ соединение
сервер
```

Если DNS не может найти домен, клиент получает ошибку разрешения имени. Это не всегда означает, что программа написана неправильно. Возможные причины:

- опечатка в домене;
- отсутствует интернет;
- DNS-сервер недоступен;
- домен больше не существует;
- доступ ограничен корпоративной сетью.

---

## 2.4. DNS: система доменных имён

**DNS — Domain Name System** — распределённая система, которая связывает удобные для человека доменные имена с техническими данными, необходимыми программам и сетевым службам.

Чаще всего DNS используют, чтобы получить IP-адрес по доменному имени:

```text
www.example.com
        ↓ DNS-запрос
192.0.2.10
        ↓ сетевое соединение
веб-сервер
```

Но DNS хранит не только IP-адреса. С его помощью можно определить:

- на какой сервер направлять веб-запрос;
- какие серверы принимают электронную почту домена;
- какие серверы являются авторитетными для зоны;
- какое имя связано с другим именем;
- какие служебные текстовые параметры опубликованы владельцем домена;
- какое доменное имя соответствует IP-адресу при обратном поиске;
- какие сервисы доступны в домене.

DNS можно представить как распределённый справочник. Он не хранится на одном сервере: разные части пространства имён обслуживаются разными организациями и DNS-серверами.

> DNS обычно помогает найти адрес сервера, но не загружает веб-страницу и не передаёт файл. После разрешения имени клиент использует другой протокол: например, HTTPS, SSH или SFTP.

## 2.5. Зачем DNS нужен пользователю и программе

Без DNS пришлось бы вводить IP-адреса вручную:

```text
https://192.0.2.10
```

Такой подход неудобен и ненадёжен:

- IP-адрес сложно запоминать;
- адрес сервера может измениться;
- один домен может вести на несколько серверов;
- один IP-адрес может обслуживать несколько доменов;
- IPv6-адреса значительно длиннее IPv4-адресов;
- сертификат HTTPS обычно проверяется относительно доменного имени;
- балансировщики и облачные платформы могут динамически менять адреса.

Доменное имя отделяет логическое имя сервиса от конкретного сетевого адреса. Владелец системы может изменить сервер или провайдера, сохранив знакомое пользователям имя.

## 2.6. Из каких частей состоит доменное имя

Рассмотрим имя:

```text
api.shop.example.com.
```

Оно читается справа налево — от общего уровня к более конкретному:

| Часть | Пример | Смысл |
|---|---|---|
| корень DNS | завершающая точка `.` | верхний уровень дерева DNS |
| домен верхнего уровня | `com` | крупная зона верхнего уровня |
| домен второго уровня | `example` | зарегистрированное имя внутри `com` |
| поддомен | `shop` | отдельная часть пространства имён владельца |
| имя узла или сервиса | `api` | конкретный узел или сервис |

Полная запись с завершающей точкой называется **FQDN — Fully Qualified Domain Name**, то есть полностью определённым доменным именем:

```text
api.shop.example.com.
```

В повседневной работе завершающую точку обычно опускают:

```text
api.shop.example.com
```

### Важные правила

- точки разделяют уровни иерархии;
- регистр букв обычно не влияет на сопоставление DNS-имён;
- `www` не является обязательной частью домена — это обычный поддомен;
- `api.example.com` и `www.example.com` могут вести на разные серверы;
- домен и URL — не одно и то же.

Сравнение:

```text
example.com                 ← доменное имя
https://example.com/catalog ← URL
```

URL дополнительно содержит схему, путь, параметры и иногда порт.

## 2.7. Иерархия DNS

DNS организован как дерево:

```text
                         корень .
                            |
              +-------------+-------------+
              |                           |
             com                         org
              |
          example
              |
       +------+------+
       |             |
      www           api
```

Основные уровни:

1. **Корневые DNS-серверы** знают, куда направить запросы к доменам верхнего уровня.
2. **Серверы домена верхнего уровня**, например `.com`, знают, какие серверы отвечают за зарегистрированный домен.
3. **Авторитетные DNS-серверы** содержат записи конкретной DNS-зоны, например `example.com`.
4. **Рекурсивный резолвер** получает запрос пользователя и при необходимости проходит цепочку поиска за него.

Пользовательская программа обычно не обращается ко всем уровням самостоятельно. Она передаёт запрос системному резолверу, а тот взаимодействует с настроенным рекурсивным DNS-сервером.

## 2.8. Что такое resolver

**Resolver**, или резолвер, — компонент, который помогает программе получить DNS-ответ.

Упрощённо существуют два уровня:

- **stub resolver** — небольшой системный компонент на компьютере пользователя;
- **recursive resolver** — DNS-сервер, который выполняет поиск ответа и возвращает его клиенту.

Когда Python, браузер или другая программа запрашивает имя, часто происходит следующая цепочка:

```text
программа
   ↓
системный resolver
   ↓
рекурсивный DNS-сервер
   ↓
корневые, TLD и авторитетные серверы при отсутствии кэша
```

Рекурсивным DNS-сервером может быть:

- сервер интернет-провайдера;
- корпоративный DNS-сервер;
- DNS-служба домашнего роутера;
- публичный DNS-сервис;
- локальный кэширующий резолвер.

В корпоративной сети нельзя самовольно менять DNS-сервер: внутренние домены и политики доступа могут работать только через утверждённую инфраструктуру.

## 2.9. Как выполняется DNS-разрешение имени

Предположим, пользователь открывает:

```text
https://api.example.com/data
```

Упрощённая последовательность:

1. Браузер или программа проверяет собственный DNS-кэш.
2. Операционная система проверяет локальный кэш.
3. Может проверяться локальный файл `hosts`.
4. Запрос передаётся настроенному рекурсивному DNS-серверу.
5. Рекурсивный сервер проверяет свой кэш.
6. Если ответа нет, он обращается к корневой инфраструктуре DNS.
7. Корневой сервер указывает серверы зоны верхнего уровня, например `.com`.
8. Сервер `.com` указывает авторитетные серверы домена `example.com`.
9. Авторитетный сервер возвращает запись для `api.example.com`.
10. Рекурсивный сервер сохраняет ответ в кэше на срок TTL.
11. IP-адрес возвращается операционной системе и программе.
12. После этого клиент устанавливает сетевое соединение с найденным адресом.
13. Для HTTPS затем выполняется TLS-рукопожатие и проверяется сертификат.
14. Только после этого отправляется HTTP-запрос.

Схема:

```text
доменное имя
    ↓ DNS
IP-адрес
    ↓ TCP-соединение
TLS-защита для HTTPS
    ↓
HTTP-запрос
    ↓
HTTP-ответ
```

DNS — это ранний этап цепочки. Если имя не разрешилось, HTTP-запрос ещё не был отправлен.

## 2.10. Рекурсивный и итеративный запрос

Эти понятия описывают разные модели поиска DNS-ответа.

### Рекурсивный запрос

Клиент просит DNS-сервер вернуть окончательный ответ либо сообщить об ошибке. Поиск за клиента выполняет рекурсивный резолвер.

```text
клиент → «Найди IP для api.example.com полностью» → рекурсивный resolver
```

### Итеративный запрос

DNS-сервер может не дать окончательный ответ, а указать, к какому серверу обратиться дальше.

```text
resolver → корневой сервер
корневой сервер → «Спроси серверы .com»
resolver → сервер .com
сервер .com → «Спроси авторитетный сервер example.com»
```

Обычная пользовательская программа чаще работает с рекурсивным DNS-сервисом, а тот использует итеративные обращения при обходе иерархии.

## 2.11. Авторитетный DNS-сервер и DNS-зона

**Авторитетный DNS-сервер** хранит официальные записи зоны и отвечает за них как источник данных.

**DNS-зона** — административно управляемая часть дерева DNS. Например, зона `example.com` может содержать записи:

```text
example.com
www.example.com
api.example.com
mail.example.com
```

Зона не всегда совпадает со всем доменом и его поддоменами: часть пространства можно делегировать другому набору DNS-серверов.

Пример делегирования:

```text
example.com          → обслуживает одна DNS-инфраструктура
internal.example.com → может быть делегирован другой инфраструктуре
```

### Не путайте три роли

| Роль | Что делает |
|---|---|
| регистратор домена | регистрирует доменное имя и позволяет указать DNS-серверы |
| DNS-хостинг | хранит и обслуживает DNS-зону |
| веб-хостинг | размещает сайт или приложение |

Одна компания может предоставлять все три услуги, но технически это разные функции.

## 2.12. Основные типы DNS-записей

DNS хранит данные в виде **resource records**, или ресурсных записей.

### A — IPv4-адрес

Связывает имя с IPv4-адресом:

```text
api.example.com.  3600  IN  A  192.0.2.10
```

Смысл:

- `api.example.com.` — имя;
- `3600` — TTL в секундах;
- `IN` — класс Internet;
- `A` — тип записи;
- `192.0.2.10` — IPv4-адрес.

### AAAA — IPv6-адрес

Связывает имя с IPv6-адресом:

```text
api.example.com.  3600  IN  AAAA  2001:db8::10
```

Название `AAAA` исторически отражает увеличенный размер адреса по сравнению с IPv4.

### CNAME — псевдоним

Указывает, что одно имя является псевдонимом другого:

```text
www.example.com.  3600  IN  CNAME  web.example.net.
```

Клиенту затем нужно разрешить целевое имя `web.example.net`.

Важно: CNAME не содержит IP-адрес напрямую.

### MX — почтовый сервер

Определяет серверы, которые принимают почту для домена:

```text
example.com.  3600  IN  MX  10 mail.example.com.
```

Число `10` — приоритет. Меньшее значение обычно означает более высокий приоритет.

### NS — авторитетный DNS-сервер

Указывает серверы, обслуживающие DNS-зону:

```text
example.com.  86400  IN  NS  ns1.example.net.
```

### TXT — текстовая запись

Хранит текстовые данные. Часто применяется для подтверждения владения доменом и почтовых политик:

```text
example.com.  3600  IN  TXT  "verification=example-value"
```

TXT не следует воспринимать как произвольное безопасное хранилище секретов: DNS-данные обычно доступны для чтения.

### PTR — обратное имя для IP-адреса

Используется при обратном DNS-поиске: от IP-адреса к имени.

```text
192.0.2.10 → host.example.com
```

PTR-записи управляются в специальных обратных зонах и обычно настраиваются владельцем адресного диапазона или провайдером.

### SOA — основная служебная запись зоны

Содержит административные параметры зоны:

- основной авторитетный сервер;
- контакт ответственного лица в специальном формате;
- серийный номер версии зоны;
- интервалы обновления;
- параметры повторных попыток;
- параметры отрицательного кэширования.

### SRV — расположение сервиса

Позволяет указать хост и порт для конкретной службы:

```text
_service._tcp.example.com.  3600  IN  SRV  10 5 443 api.example.com.
```

SRV содержит приоритет, вес, порт и целевой хост.

### CAA — разрешённые центры сертификации

Помогает владельцу домена указать, какие центры сертификации могут выпускать сертификаты для домена.

DNS поддерживает и другие типы записей. Выбирать тип нужно по назначению, а не по внешнему сходству данных.

## 2.13. Что такое TTL и DNS-кэш

**TTL — Time To Live** — время в секундах, в течение которого DNS-ответ может храниться в кэше.

Пример:

```text
api.example.com.  300  IN  A  192.0.2.10
```

TTL `300` означает, что кэширующий компонент может использовать ответ до пяти минут, прежде чем запросить обновление.

Кэш может находиться:

- в приложении;
- в браузере;
- в операционной системе;
- в домашнем роутере;
- на корпоративном DNS-сервере;
- на рекурсивном DNS-сервере провайдера.

### Почему изменение DNS видно не сразу

После изменения записи часть клиентов может продолжать получать старый ответ, пока не истечёт TTL ранее закэшированной записи.

Поэтому фраза «DNS ещё не распространился» является упрощением. Обычно речь идёт о сочетании факторов:

- старые ответы ещё находятся в кэшах;
- разные резолверы обновляют данные в разное время;
- авторитетные серверы могут быть настроены несогласованно;
- делегирование могло быть изменено не полностью;
- приложение может иметь собственный кэш;
- локальный файл `hosts` может переопределять DNS.

### Слишком маленький TTL

Плюсы:

- изменения становятся видимыми быстрее после истечения старого TTL.

Минусы:

- увеличивается количество DNS-запросов;
- возрастает нагрузка на резолверы и авторитетные серверы;
- уменьшается польза кэширования.

### Слишком большой TTL

Плюсы:

- меньше DNS-запросов;
- выше эффективность кэша.

Минусы:

- аварийное переключение адреса может занять больше времени для клиентов со старым кэшем.

TTL выбирают с учётом стабильности сервиса и требований к переключению.

## 2.14. Отрицательное кэширование

DNS может кэшировать не только найденные записи, но и отрицательные ответы, например информацию о том, что имя не существует.

Пример ситуации:

1. Клиент запросил `new-api.example.com` до создания записи.
2. DNS вернул ответ, что имя не существует.
3. Отрицательный ответ попал в кэш.
4. Администратор создал запись.
5. Часть клиентов ещё некоторое время продолжает получать отрицательный результат.

Поэтому после создания нового имени проблема может сохраняться до истечения периода отрицательного кэширования.

## 2.15. DNS и файл hosts

Операционные системы поддерживают локальный файл `hosts`, который может связывать имя с IP-адресом без обращения к обычному DNS.

Типичная строка:

```text
127.0.0.1 localhost
```

Файл может использоваться для:

- локальной разработки;
- временного тестирования;
- доступа к лабораторному стенду;
- блокировки отдельных имён в контролируемой среде.

Но у подхода есть ограничения:

- записи действуют только на конкретном компьютере;
- файл трудно централизованно поддерживать;
- устаревшая запись может направлять клиента на неправильный адрес;
- вредоносное изменение файла может перенаправить пользователя.

Не изменяйте `hosts` на рабочем устройстве без понимания последствий и разрешения администратора.

## 2.16. DNS использует UDP или TCP

Классический DNS обычно использует порт `53`:

- UDP — для многих обычных запросов и ответов;
- TCP — когда это требуется протоколом, размером ответа или операцией.

Нельзя считать, что DNS всегда работает только по UDP. Современная DNS-инфраструктура также может применять:

- **DoT — DNS over TLS**: DNS через TLS, обычно порт 853;
- **DoH — DNS over HTTPS**: DNS-сообщения через HTTPS;
- другие защищённые транспортные механизмы в зависимости от системы.

Сетевые политики организации могут разрешать только утверждённые DNS-механизмы. Самовольное включение внешнего DoH может нарушить внутреннее разрешение имён, мониторинг или требования безопасности.

## 2.17. DNS, DoH, DoT и DNSSEC — не одно и то же

Эти технологии решают разные задачи.

| Технология | Что защищает | Чего не гарантирует |
|---|---|---|
| обычный DNS | выполняет разрешение имён | конфиденциальность и криптографическую проверку данных |
| DoT | шифрует канал между клиентом и DNS-сервисом через TLS | не заменяет DNSSEC |
| DoH | передаёт DNS-запросы через HTTPS | не доказывает правильность самой DNS-записи без дополнительных механизмов |
| DNSSEC | позволяет проверять происхождение и целостность подписанных DNS-данных | не шифрует DNS-запросы и не скрывает имена |

### DNSSEC

DNSSEC добавляет цифровые подписи к DNS-данным и позволяет validating-resolver проверить:

- что ответ относится к подписанной зоне;
- что данные не были незаметно изменены;
- что существует цепочка доверия от доверенной точки.

DNSSEC не обеспечивает конфиденциальность. Наблюдатель сети всё ещё может видеть обычный незашифрованный DNS-запрос, если DoH, DoT или другой защищённый транспорт не используется.

### DoH и DoT

DoH и DoT защищают транспорт между клиентом и выбранным DNS-сервисом от простого просмотра и изменения по пути. Но клиент всё равно доверяет выбранному DNS-сервису, а дальнейшая обработка запроса зависит от его политики и инфраструктуры.

## 2.18. DNS и HTTPS работают совместно

DNS и HTTPS решают разные задачи:

- DNS помогает найти адрес;
- HTTPS защищает последующий HTTP-обмен и проверяет серверный сертификат.

Важно понимать:

- успешный DNS-ответ не доказывает, что сайт безопасен;
- HTTPS-сертификат проверяется для доменного имени;
- неправильный DNS-ответ может направить клиента не туда, но корректная проверка TLS-сертификата способна остановить соединение, если сертификат не соответствует имени;
- отключение проверки сертификата разрушает важный защитный барьер;
- DNSSEC и HTTPS дополняют друг друга, но не заменяют друг друга.

## 2.19. Балансировка нагрузки через DNS

Одно доменное имя может иметь несколько A- или AAAA-записей:

```text
api.example.com → 192.0.2.10
api.example.com → 192.0.2.11
api.example.com → 192.0.2.12
```

Это может применяться для распределения запросов, отказоустойчивости или географического направления трафика.

Однако DNS-балансировка имеет особенности:

- клиенты и резолверы кэшируют ответы;
- порядок адресов может меняться;
- приложение может использовать только один из полученных адресов;
- отказавший адрес может оставаться в кэше до истечения TTL;
- разные пользователи могут получать разные ответы.

Поэтому DNS может быть частью балансировки, но не заменяет полноценные механизмы проверки здоровья и управления трафиком.

## 2.20. Внутренний DNS и split-horizon DNS

В организации одно и то же имя иногда возвращает разные ответы в зависимости от места запроса.

Пример:

```text
api.example.com из внутренней сети → 10.20.0.15
api.example.com из интернета       → 203.0.113.25
```

Такую схему часто называют **split-horizon DNS** или split DNS.

Возможные последствия для новичка:

- сервис работает через корпоративный VPN, но не работает без VPN;
- публичный DNS не знает внутреннее имя;
- внешний DoH обходит корпоративный DNS и ломает разрешение внутренних имён;
- результаты `nslookup` на рабочем и домашнем компьютере различаются.

Это не обязательно ошибка сервиса. Сначала нужно определить, из какой сети выполняется запрос и какой DNS-сервер используется.

## 2.21. Основные DNS-ошибки

### NXDOMAIN

Означает, что запрошенного доменного имени не существует в ответившей DNS-системе.

Возможные причины:

- опечатка;
- запись ещё не создана;
- имя удалено;
- клиент использует не тот DNS-сервер;
- внутреннее имя запрашивается вне корпоративной сети.

### SERVFAIL

DNS-сервер не смог корректно завершить обработку запроса.

Возможные причины:

- проблема авторитетного сервера;
- ошибка DNSSEC-валидации;
- неисправность или перегрузка резолвера;
- несогласованная конфигурация зоны;
- временная сетевая проблема.

### Timeout

Ответ не получен за допустимое время.

Возможные причины:

- DNS-сервер недоступен;
- трафик блокируется;
- потеря пакетов;
- проблема VPN;
- неверно настроен адрес DNS-сервера.

### No answer / NODATA

Имя может существовать, но запись запрошенного типа отсутствует. Например, у имени есть A-запись, но нет MX-записи.

Это отличается от NXDOMAIN, где не существует само имя.

### Старый адрес

Причины:

- не истёк TTL;
- кэш приложения;
- локальный DNS-кэш;
- запись в `hosts`;
- разные авторитетные серверы возвращают несогласованные данные.

## 2.23. Получение IP-адресов через Python

Модуль `socket` входит в стандартную библиотеку Python. Функция `getaddrinfo()` удобнее простого `gethostbyname()`, потому что может возвращать и IPv4-, и IPv6-адреса.

```python
import socket  # Импортируем стандартный модуль socket для сетевых операций и разрешения имён.

hostname = "example.com"  # Сохраняем доменное имя, для которого хотим получить сетевые адреса.

try:  # Начинаем блок обработки ожидаемой ошибки DNS-разрешения.
    address_info = socket.getaddrinfo(hostname, None)  # Запрашиваем у системного resolver все доступные адреса домена.
    unique_addresses = sorted({item[4][0] for item in address_info})  # Извлекаем IP-адреса и удаляем повторяющиеся значения через множество.

    print(f"Домен: {hostname}")  # Выводим имя, которое было передано на разрешение.
    for ip_address in unique_addresses:  # Перебираем все уникальные IPv4- и IPv6-адреса.
        print(f"IP-адрес: {ip_address}")  # Выводим очередной найденный IP-адрес.
except socket.gaierror as error:  # Перехватываем специализированную ошибку разрешения имени.
    print(f"Не удалось разрешить доменное имя: {error}")  # Сообщаем пользователю, что DNS-разрешение завершилось ошибкой.
```

Что важно:

- результат зависит от используемого DNS-сервера и сети;
- адресов может быть несколько;
- порядок адресов не следует считать постоянным;
- наличие IP-адреса не гарантирует доступность веб-сервиса;
- после DNS-разрешения ещё нужно установить соединение с нужным портом.

## 2.24. Определение семейства IP-адреса через Python

```python
import socket  # Импортируем модуль socket для доступа к константам сетевых семейств.

hostname = "example.com"  # Задаём доменное имя для проверки IPv4- и IPv6-адресов.
address_info = socket.getaddrinfo(hostname, 443, type=socket.SOCK_STREAM)  # Запрашиваем адреса для потокового соединения с типичным HTTPS-портом 443.

for family, socket_type, protocol, canonical_name, socket_address in address_info:  # Разбираем каждую структуру, возвращённую getaddrinfo().
    ip_address = socket_address[0]  # Извлекаем IP-адрес из структуры адреса сокета.

    if family == socket.AF_INET:  # Проверяем, относится ли адрес к семейству IPv4.
        ip_version = "IPv4"  # Сохраняем текстовую метку IPv4.
    elif family == socket.AF_INET6:  # Проверяем, относится ли адрес к семейству IPv6.
        ip_version = "IPv6"  # Сохраняем текстовую метку IPv6.
    else:  # Обрабатываем редкое неизвестное семейство адресов.
        ip_version = "Другое семейство"  # Сохраняем нейтральную подпись для неизвестного типа.

    print(f"{ip_version}: {ip_address}")  # Выводим версию IP и найденный адрес.
```

В выводе адреса могут повторяться, потому что `getaddrinfo()` возвращает варианты для разных протокольных параметров. Если нужны только уникальные адреса, их следует дополнительно дедуплицировать.

## 2.25. Обратный DNS-поиск через Python

Обратный DNS-поиск пытается получить имя по IP-адресу. Наличие PTR-записи не гарантируется.

```python
import socket  # Импортируем стандартный модуль socket для обратного DNS-поиска.

ip_address = "192.0.2.10"  # Указываем документационный IP-адрес, зарезервированный для примеров.

try:  # Начинаем блок обработки ожидаемой ошибки обратного разрешения.
    host_name, aliases, addresses = socket.gethostbyaddr(ip_address)  # Запрашиваем основное имя, псевдонимы и связанные адреса.
    print(f"Основное имя: {host_name}")  # Выводим основное имя из PTR-ответа.
    print(f"Псевдонимы: {aliases}")  # Выводим список псевдонимов, если они существуют.
    print(f"Адреса: {addresses}")  # Выводим адреса, связанные с полученным именем.
except socket.herror as error:  # Перехватываем специализированную ошибку отсутствия обратной записи.
    print(f"Обратная DNS-запись не найдена: {error}")  # Сообщаем, что для адреса не удалось получить PTR-имя.
```

Обратное имя не следует использовать как единственное доказательство владельца или назначения сервера. PTR — это административная DNS-запись, а не криптографическое подтверждение личности.

## 2.26. Запрос конкретных DNS-записей через dnspython

Стандартный `socket` удобен для получения адресов, но не предназначен для детальной работы со всеми типами DNS-записей. Для этого можно использовать библиотеку `dnspython`.

Установка:

```bash
# Устанавливаем библиотеку dnspython в активное Python-окружение.
pip install dnspython
```

Пример запроса A-записей:

```python
import dns.exception  # Импортируем базовые DNS-исключения библиотеки dnspython.
import dns.resolver  # Импортируем resolver для выполнения DNS-запросов.

hostname = "example.com"  # Задаём доменное имя для DNS-запроса.
record_type = "A"  # Указываем, что хотим получить IPv4-адреса из A-записей.

try:  # Начинаем блок обработки ожидаемых DNS-ошибок.
    answers = dns.resolver.resolve(hostname, record_type, lifetime=5.0)  # Выполняем запрос с общим лимитом ожидания пять секунд.

    print(f"Записи типа {record_type} для {hostname}:")  # Выводим заголовок результата.
    for answer in answers:  # Перебираем все записи, полученные в DNS-ответе.
        print(answer.to_text())  # Преобразуем очередную DNS-запись в текст и выводим её.
except dns.resolver.NXDOMAIN:  # Обрабатываем случай, когда доменное имя не существует.
    print("Доменное имя не существует.")  # Выводим понятное сообщение об NXDOMAIN.
except dns.resolver.NoAnswer:  # Обрабатываем случай, когда имя существует, но запрошенного типа записи нет.
    print(f"Для домена нет записи типа {record_type}.")  # Объясняем отличие отсутствующей записи от отсутствующего домена.
except dns.resolver.NoNameservers:  # Обрабатываем ситуацию, когда доступные DNS-серверы не смогли дать пригодный ответ.
    print("DNS-серверы не смогли обработать запрос.")  # Выводим сообщение о проблеме на стороне DNS-инфраструктуры.
except dns.exception.Timeout:  # Обрабатываем превышение времени ожидания DNS-ответа.
    print("Истекло время ожидания DNS-ответа.")  # Сообщаем пользователю о тайм-ауте.
```

## 2.27. Получение MX-записей и приоритетов через Python

```python
import dns.exception  # Импортируем DNS-исключения для обработки тайм-аутов.
import dns.resolver  # Импортируем resolver библиотеки dnspython.

mail_domain = "example.com"  # Задаём домен, для которого хотим узнать почтовые серверы.

try:  # Начинаем блок обработки ожидаемых ошибок DNS-запроса.
    mx_answers = dns.resolver.resolve(mail_domain, "MX", lifetime=5.0)  # Запрашиваем MX-записи с лимитом ожидания пять секунд.
    sorted_answers = sorted(mx_answers, key=lambda answer: answer.preference)  # Сортируем записи по числовому приоритету от меньшего к большему.

    for answer in sorted_answers:  # Перебираем отсортированные MX-записи.
        priority = answer.preference  # Извлекаем приоритет почтового сервера.
        mail_server = str(answer.exchange).rstrip(".")  # Получаем имя сервера и убираем завершающую точку для удобного вывода.
        print(f"Приоритет {priority}: {mail_server}")  # Выводим приоритет и имя почтового сервера.
except dns.resolver.NXDOMAIN:  # Обрабатываем отсутствие доменного имени.
    print("Домен не существует.")  # Выводим понятное сообщение об ошибке.
except dns.resolver.NoAnswer:  # Обрабатываем отсутствие MX-записей у существующего имени.
    print("MX-записи не найдены.")  # Сообщаем, что почтовые записи отсутствуют.
except dns.exception.Timeout:  # Обрабатываем превышение времени ожидания.
    print("DNS-запрос завершился по тайм-ауту.")  # Выводим сообщение о тайм-ауте.
```

## 2.28. Получение TTL через Python

TTL относится к набору записей в DNS-ответе. В `dnspython` его можно получить через объект `rrset`.

```python
import dns.exception  # Импортируем DNS-исключения для корректной обработки ошибок.
import dns.resolver  # Импортируем DNS-resolver для выполнения запроса.

hostname = "example.com"  # Задаём имя, TTL которого хотим посмотреть.

try:  # Начинаем блок обработки ожидаемых ошибок.
    answers = dns.resolver.resolve(hostname, "A", lifetime=5.0)  # Запрашиваем A-записи домена.
    ttl_seconds = answers.rrset.ttl  # Извлекаем TTL набора ресурсных записей в секундах.

    print(f"TTL: {ttl_seconds} секунд")  # Выводим TTL в секундах.
    for answer in answers:  # Перебираем адреса из ответа.
        print(f"IPv4: {answer.to_text()}")  # Выводим каждый IPv4-адрес.
except dns.resolver.NXDOMAIN:  # Обрабатываем отсутствие домена.
    print("Домен не существует.")  # Выводим понятное сообщение.
except dns.resolver.NoAnswer:  # Обрабатываем отсутствие A-записи.
    print("A-запись отсутствует.")  # Сообщаем, что домен существует без записи нужного типа.
except dns.exception.Timeout:  # Обрабатываем тайм-аут.
    print("DNS-сервер не ответил за отведённое время.")  # Выводим сообщение о проблеме времени ожидания.
```

Фактический срок хранения ответа конкретным компонентом может зависеть от реализации и локальной политики. TTL показывает значение, полученное в DNS-ответе, но не раскрывает все промежуточные кэши.

## 2.29. Мини-диагностика домена через Python

Следующий пример объединяет несколько безопасных проверок:

- синтаксически принимает доменное имя;
- получает IPv4- и IPv6-адреса через системный resolver;
- сообщает специализированную ошибку;
- не пытается самостоятельно обходить политики DNS;
- не отключает проверки безопасности.

```python
import socket  # Импортируем стандартный модуль socket для системного DNS-разрешения.

hostname = "example.com"  # Задаём доменное имя для диагностики.

try:  # Начинаем обработку ожидаемой ошибки разрешения имени.
    address_info = socket.getaddrinfo(hostname, 443, type=socket.SOCK_STREAM)  # Получаем адреса, подходящие для потокового соединения с HTTPS-портом.
    addresses = sorted({item[4][0] for item in address_info})  # Извлекаем уникальные IP-адреса из результата.

    if addresses:  # Проверяем, что список адресов не пуст.
        print(f"DNS-разрешение выполнено для {hostname}.")  # Сообщаем об успешном разрешении имени.
        for address in addresses:  # Перебираем все уникальные адреса.
            print(f"Найден адрес: {address}")  # Выводим очередной найденный адрес.
    else:  # Обрабатываем редкую ситуацию пустого ответа без исключения.
        print("DNS-ответ не содержит пригодных адресов.")  # Сообщаем, что адреса не были получены.
except socket.gaierror as error:  # Перехватываем ошибку системного resolver.
    print(f"DNS-разрешение не выполнено: {error}")  # Выводим текст ошибки без заявления о причине, которую ещё нужно диагностировать.
```

Этот код проверяет только разрешение имени. Он не доказывает, что:

- порт 443 доступен;
- сервер принимает HTTPS;
- сертификат корректен;
- HTTP-ресурс существует;
- пользователь имеет право доступа.

Каждый следующий уровень нужно проверять отдельно.

## 2.30. Пошаговая диагностика проблемы DNS

Если приложение сообщает ошибку разрешения имени, используйте последовательность:

1. Проверьте написание домена.
2. Убедитесь, что это домен, а не полный URL с ошибкой формата.
3. Проверьте подключение к сети.
4. Определите, нужен ли корпоративный VPN.
5. Выполните `nslookup`, `Resolve-DnsName` или `dig`.
6. Посмотрите, какой DNS-сервер дал ответ.
7. Сравните результат в рабочей и другой разрешённой сети.
8. Проверьте локальный файл `hosts`.
9. Учитывайте TTL и отрицательный кэш.
10. Если домен корпоративный, обратитесь к администратору DNS.
11. Если запись менялась, проверьте все авторитетные серверы.
12. Не отключайте TLS-проверку: она не исправляет DNS.
13. Не заменяйте домен IP-адресом в production-коде без архитектурного решения.

Формат фиксации проблемы:

```text
наблюдение → домен → тип записи → DNS-сервер → полученный ответ → сеть/VPN → время проверки → ожидаемый результат
```

Пример:

```text
Наблюдение: NXDOMAIN
Домен: internal-api.example.com
Тип: A
DNS-сервер: корпоративный resolver
Сеть: домашняя, VPN отключён
Ожидание: внутренний адрес сервиса
Следующий шаг: повторить проверку через утверждённый VPN
```

## 2.31. Типовые ошибки новичка при работе с DNS

### Ошибка 1. Считать DNS и интернет одним и тем же

Интернет-соединение может работать, но конкретный DNS-сервер — нет. И наоборот: DNS может вернуть адрес, но сервер не отвечает на порту.

### Ошибка 2. Считать IP-адрес постоянным

Облачный сервис может менять адреса. Не следует жёстко записывать найденный IP вместо доменного имени без обоснованной архитектуры.

### Ошибка 3. Путать NXDOMAIN и отсутствие записи нужного типа

NXDOMAIN означает отсутствие имени. NoAnswer означает, что имя может существовать, но нужного типа записи нет.

### Ошибка 4. Ожидать мгновенного изменения DNS

Старые ответы могут оставаться в кэшах до истечения TTL, а отрицательные ответы также могут кэшироваться.

### Ошибка 5. Считать CNAME IP-адресом

CNAME указывает на другое имя. Для получения адреса требуется дальнейшее разрешение целевого имени.

### Ошибка 6. Считать DNSSEC шифрованием

DNSSEC проверяет происхождение и целостность подписанных данных, но не скрывает запросы.

### Ошибка 7. Считать DoH проверкой правильности записи

DoH защищает канал до DNS-сервиса. Корректность и доверие к данным требуют отдельного рассмотрения.

### Ошибка 8. Самовольно менять корпоративный DNS

Внутренние имена, политики и журналы могут зависеть от утверждённого resolver.

### Ошибка 9. Отключать TLS-проверку из-за DNS-ошибки

TLS начинается после DNS-разрешения и соединения. Отключение проверки сертификата не исправляет отсутствие DNS-ответа и создаёт риск безопасности.

### Ошибка 10. Публиковать внутренние имена и адреса

Имена внутренних систем, IP-адреса, структура зон и диагностические логи могут быть чувствительной информацией. Передавайте их только по разрешённым каналам.

## 2.32. Чек-лист понимания DNS

После изучения раздела студент должен уметь:

- объяснить назначение DNS простыми словами;
- отличить доменное имя от URL;
- прочитать доменное имя справа налево по уровням;
- объяснить роли stub resolver, recursive resolver и authoritative server;

- провести первичную диагностику без отключения защитных механизмов.

# 3. HTTP: обмен запросами и ответами

## 3.1. Что такое HTTP

**HTTP — Hypertext Transfer Protocol** — прикладной протокол обмена сообщениями между клиентом и сервером.

HTTP используется не только для HTML-страниц. Через него можно передавать:

- текст;
- HTML;
- JSON;
- XML;
- изображения;
- документы;
- архивы;
- видео;
- ответы API.

HTTP считается протоколом без сохранения состояния: отдельный запрос сам по себе не обязан знать о предыдущем запросе. Сайты могут добавлять состояние через cookies, сессии, токены и серверные хранилища, но это уже дополнительная логика поверх базового обмена HTTP-сообщениями.

## 3.2. Из чего состоит HTTP-запрос

Упрощённый HTTP-запрос содержит:

1. метод;
2. адрес ресурса;
3. заголовки;
4. тело запроса, если оно требуется.

Пример логики запроса:

```text
GET /products HTTP/1.1
Host: example.com
Accept: application/json
```

Здесь:

- `GET` — метод;
- `/products` — путь к ресурсу;
- `Host` — сервер;
- `Accept` — желаемый формат ответа.

## 3.3. Основные HTTP-методы

| Метод | Базовый смысл | Пример |
|---|---|---|
| GET | получить ресурс | получить список товаров |
| POST | передать данные для обработки или создать ресурс | создать заказ |
| PUT | полностью заменить представление ресурса | заменить карточку клиента |
| PATCH | частично изменить ресурс | изменить только телефон |
| DELETE | удалить ресурс | удалить черновик |
| HEAD | получить заголовки без тела ответа | проверить размер файла |
| OPTIONS | узнать поддерживаемые возможности | проверить доступные методы |

Подробная работа методов особенно важна при изучении REST API. В этом материале основной практический пример будет построен на безопасном методе GET.

## 3.4. Из чего состоит HTTP-ответ

Сервер возвращает:

1. статусный код;
2. заголовки ответа;
3. тело ответа.

Упрощённый пример:

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256

<html>...</html>
```

## 3.5. Группы статусных кодов

| Группа | Смысл | Примеры |
|---|---|---|
| 1xx | информационные ответы | 100 Continue |
| 2xx | запрос успешно обработан | 200 OK, 201 Created |
| 3xx | перенаправление | 301 Moved Permanently, 302 Found |
| 4xx | проблема в запросе клиента или правах | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found |
| 5xx | ошибка на стороне сервера | 500 Internal Server Error, 503 Service Unavailable |

Важно: наличие HTTP-ответа ещё не означает успех. Сервер может вернуть ответ со статусом 404 или 500. Поэтому код должен проверять статус.

# 4. Подготовка Python для HTTP-примеров

## 4.1. Библиотека requests

Для простых HTTP-запросов удобно использовать библиотеку `requests`.

Она не входит в стандартную библиотеку Python, поэтому её нужно установить.

```bash
# Устанавливаем библиотеку requests в текущее Python-окружение.

```

Проверка установки:

```python
import requests  # Импортируем библиотеку requests для выполнения HTTP-запросов.

print(requests.__version__)  # Выводим установленную версию библиотеки.
```

Если появляется ошибка `ModuleNotFoundError`, библиотека установлена не в то Python-окружение, из которого запускается код.

## 4.2. Первый HTTPS-запрос

```python
import requests  # Импортируем библиотеку requests.

url = "https://example.com"  # Сохраняем адрес безопасного демонстрационного сайта.
response = requests.get(url, timeout=10)  # Отправляем GET-запрос и ограничиваем ожидание ответа десятью секундами.
response.raise_for_status()  # Создаём исключение, если сервер вернул ошибочный статус 4xx или 5xx.

print("Статус:", response.status_code)  # Выводим числовой HTTP-статус ответа.
print("Финальный URL:", response.url)  # Выводим адрес после возможных перенаправлений.
print("Тип содержимого:", response.headers.get("Content-Type"))  # Получаем тип данных из заголовков ответа.
print("Первые 200 символов:")  # Выводим поясняющий заголовок перед фрагментом страницы.
print(response.text[:200])  # Показываем первые 200 символов текстового тела ответа.
```

Что происходит по шагам:

1. Python создаёт HTTP-клиент;
2. клиент обращается к `example.com` по HTTPS;
3. сервер возвращает статус, заголовки и HTML;
4. код проверяет статус;
5. код показывает часть результата.

## 4.3. Почему нужен timeout

Без `timeout` программа может ждать ответ слишком долго, если сервер или сеть перестали отвечать.

```python
import requests  # Импортируем библиотеку для HTTP-запросов.

url = "https://example.com"  # Задаём адрес сервера.
response = requests.get(url, timeout=5)  # Ограничиваем ожидание сетевой активности пятью секундами.
print(response.status_code)  # Выводим статус, если ответ был успешно получен.
```

`timeout=5` не гарантирует, что вся загрузка завершится ровно за пять секунд. Он ограничивает ожидание сетевой активности согласно правилам библиотеки `requests`.

## 4.4. Обработка сетевых ошибок

Новичку важно не только получить успешный ответ, но и корректно обработать неуспешный сценарий.

```python
import requests  # Импортируем requests для выполнения HTTP-запроса.

url = "https://example.com"  # Указываем адрес ресурса.

try:  # Начинаем блок, в котором может возникнуть ожидаемая сетевая ошибка.
    response = requests.get(url, timeout=10)  # Отправляем GET-запрос с ограничением времени ожидания.
    response.raise_for_status()  # Проверяем, не относится ли статус ответа к ошибочным 4xx или 5xx.
    print("Запрос выполнен успешно.")  # Сообщаем об успешном завершении запроса.
    print("Статус:", response.status_code)  # Показываем полученный статус ответа.
except requests.exceptions.Timeout:  # Обрабатываем ситуацию, когда сервер слишком долго не отвечает.
    print("Сервер не ответил за установленное время.")  # Выводим понятное сообщение об ошибке ожидания.
except requests.exceptions.ConnectionError:  # Обрабатываем проблемы DNS, сети или установления соединения.
    print("Не удалось установить соединение с сервером.")  # Выводим сообщение о проблеме подключения.
except requests.exceptions.HTTPError as error:  # Обрабатываем неуспешный HTTP-статус.
    print("Сервер вернул HTTP-ошибку:", error)  # Показываем информацию об HTTP-ошибке.
except requests.exceptions.RequestException as error:  # Обрабатываем остальные ошибки, создаваемые requests.
    print("Произошла ошибка запроса:", error)  # Выводим описание прочей ошибки запроса.
```

Обратите внимание: используется не общий `except:`, а конкретные типы ошибок. Это помогает понять, что именно произошло.

## 4.5. Просмотр заголовков ответа

```python
import requests  # Импортируем библиотеку requests.

url = "https://example.com"  # Задаём URL для запроса.
response = requests.get(url, timeout=10)  # Получаем ответ сервера.
response.raise_for_status()  # Проверяем успешность HTTP-статуса.

for header_name, header_value in response.headers.items():  # Перебираем все заголовки ответа как пары имя-значение.
    print(f"{header_name}: {header_value}")  # Печатаем каждый заголовок в удобном формате.
```

Часто встречаются заголовки:

- `Content-Type` — тип тела ответа;
- `Content-Length` — размер тела, если сервер его указал;
- `Date` — время формирования ответа;
- `Server` — информация о серверном ПО, если сервер её раскрывает;
- `Cache-Control` — правила кеширования;
- `Location` — адрес перенаправления.

## 4.6. Скачивание файла по HTTPS

При загрузке бинарного файла нужно использовать `response.content`, а не `response.text`.

```python
from pathlib import Path  # Импортируем Path для безопасной работы с путями к файлам.
import requests  # Импортируем requests для загрузки данных по HTTPS.

url = "https://example.com"  # Указываем демонстрационный URL; в реальной задаче здесь будет адрес файла.
output_path = Path("downloaded_page.html")  # Задаём локальное имя файла, в который будет сохранён ответ.

response = requests.get(url, timeout=10)  # Загружаем ресурс с ограничением времени ожидания.
response.raise_for_status()  # Проверяем, что сервер не вернул ошибку 4xx или 5xx.
output_path.write_bytes(response.content)  # Сохраняем полученные байты в локальный файл.

print("Файл сохранён:", output_path.resolve())  # Показываем полный путь к созданному файлу.
print("Размер в байтах:", output_path.stat().st_size)  # Показываем размер сохранённого файла.
```

Для очень больших файлов лучше использовать потоковую загрузку частями. Этот вариант будет уместен после освоения базового запроса.

# 5. HTTPS: защищённый HTTP

## 5.1. Что меняет HTTPS

HTTPS использует семантику HTTP, но передаёт данные через защищённое TLS-соединение.

TLS обеспечивает три ключевых свойства:

- **конфиденциальность** — посторонний наблюдатель не должен читать содержимое обмена;
- **целостность** — данные не должны незаметно измениться в пути;
- **проверку подлинности сервера** — клиент проверяет сертификат сервера и соответствие доменному имени.

Упрощённо:

```text
HTTP:
клиент ---- открытые данные ---- сервер

HTTPS:
клиент ==== защищённый TLS-канал ==== сервер
```

## 5.2. Сертификат сервера

При HTTPS сервер предъявляет цифровой сертификат. Клиент проверяет, среди прочего:

- кем выдан сертификат;
- не истёк ли срок действия;
- подходит ли сертификат указанному домену;
- доверяет ли система цепочке сертификации.

Если проверка не проходит, библиотека обычно завершает соединение ошибкой. Это полезное защитное поведение.

## 5.3. Нельзя отключать проверку сертификата без необходимости

Иногда в интернете встречается такой код:

```python
response = requests.get("https://example.com", verify=False)  # Плохой шаблон: отключает проверку TLS-сертификата.
```

Для обычного рабочего кода этот подход небезопасен. Он может скрыть неправильный сертификат или атаку посредника.

Правильный базовый вариант:

```python
import requests  # Импортируем библиотеку requests.

url = "https://example.com"  # Используем URL со схемой HTTPS.
response = requests.get(url, timeout=10)  # Выполняем запрос с включённой по умолчанию проверкой сертификата.
response.raise_for_status()  # Проверяем HTTP-статус ответа.

print("HTTPS-запрос выполнен успешно.")  # Сообщаем об успешном защищённом запросе.
```

Если внутри организации используется собственный центр сертификации, правильное решение — настроить доверенный сертификат или передать путь к корпоративному CA-файлу, а не отключать проверку.

## 5.4. HTTP и HTTPS — не два разных формата данных

И HTTP, и HTTPS могут передавать HTML, JSON, изображения и другие данные. Главное отличие состоит в защите канала передачи.

| Критерий | HTTP | HTTPS |
|---|---|---|
| базовая семантика запросов | есть | есть |
| TLS-защита | нет | да |
| типичный порт | 80 | 443 |
| проверка сертификата сервера | нет | да |
| подходит для паролей и токенов | нет | при корректной настройке |

Практическое правило: для сайтов, API, авторизации и передачи рабочих данных следует использовать HTTPS.

# 6. Перенаправления HTTP

Сервер может сообщить клиенту, что ресурс находится по другому адресу.

Например:

```text
http://example.com
        ↓ 301 или 302
https://example.com
```

Библиотека `requests` обычно автоматически следует перенаправлениям для GET-запроса.

```python
import requests  # Импортируем библиотеку requests.

url = "http://example.com"  # Используем HTTP-адрес, который сервер может перенаправить на HTTPS.
response = requests.get(url, timeout=10)  # Выполняем запрос и разрешаем стандартную обработку перенаправлений.

print("Исходный адрес:", url)  # Выводим адрес, который был указан в коде.
print("Финальный адрес:", response.url)  # Выводим адрес после всех выполненных перенаправлений.
print("Количество перенаправлений:", len(response.history))  # Показываем число промежуточных ответов.

for previous_response in response.history:  # Перебираем промежуточные ответы из истории перенаправлений.
    print(previous_response.status_code, previous_response.headers.get("Location"))  # Показываем статус и новый адрес каждого перехода.
```

Перенаправление не всегда является ошибкой. Но неожиданное перенаправление на незнакомый домен требует проверки.

# 7. FTP: классическая передача файлов

## 7.1. Что такое FTP

**FTP — File Transfer Protocol** — протокол для передачи файлов между клиентом и сервером.

FTP позволяет:

- просматривать список файлов;
- переходить между каталогами;
- скачивать файлы;
- загружать файлы;
- создавать и удалять каталоги, если есть права;
- переименовывать и удалять файлы, если это разрешено.

Классический FTP использует отдельное управляющее соединение для команд и отдельное соединение для передачи данных.

## 7.2. Важное ограничение безопасности FTP

Обычный FTP не обеспечивает современную защиту учётных данных и передаваемой информации. В общем случае логин, пароль и содержимое могут быть доступны для перехвата внутри небезопасной сети.

Поэтому для рабочих данных предпочтительны:

- **FTPS** — FTP с TLS-защитой;
- **SFTP** — отдельный протокол передачи файлов через SSH;
- **HTTPS-загрузка** — если система предоставляет веб-интерфейс или API.

Не путайте:

```text
FTP   = отдельный протокол передачи файлов
FTPS  = FTP, защищённый TLS
SFTP  = передача файлов через SSH
```

## 7.3. Модуль ftplib

Модуль `ftplib` входит в стандартную библиотеку Python. Устанавливать его через pip не нужно.

```python
from ftplib import FTP  # Импортируем FTP-клиент из стандартной библиотеки Python.

print(FTP)  # Выводим класс FTP, чтобы убедиться, что модуль доступен.
```

## 7.4. Безопасное хранение параметров подключения

Нельзя записывать реальный пароль прямо в код, особенно если файл будет отправлен преподавателю или сохранён в Git.

Плохой пример:

```python
password = "MyRealPassword123"  # Плохой пример: секрет хранится прямо в исходном коде.
```

Более безопасный базовый вариант — переменные окружения.

Windows PowerShell:

```powershell
# Сохраняем имя FTP-сервера в переменную окружения текущего окна PowerShell.
$env:FTP_HOST="ftp.company.example"
# Сохраняем имя пользователя в переменную окружения текущего окна PowerShell.
$env:FTP_USER="student"
# Сохраняем пароль в переменную окружения текущего окна PowerShell.
$env:FTP_PASSWORD="replace_with_real_password"
```

Linux или macOS:

```bash
# Сохраняем имя FTP-сервера в переменную окружения текущего терминала.
export FTP_HOST="ftp.company.example"
# Сохраняем имя пользователя в переменную окружения текущего терминала.
export FTP_USER="student"
# Сохраняем пароль в переменную окружения текущего терминала.
export FTP_PASSWORD="replace_with_real_password"
```

Переменные, заданные таким способом, обычно действуют только в текущем окне терминала.

## 7.5. Просмотр файлов на FTP-сервере

Следующий код является шаблоном. Для запуска замените параметры окружения на данные сервера, доступ к которому вам официально предоставлен.

```python
import os  # Импортируем os для чтения переменных окружения.
from ftplib import FTP, all_errors  # Импортируем FTP-клиент и набор стандартных FTP-исключений.

host = os.getenv("FTP_HOST")  # Читаем адрес FTP-сервера из переменной окружения.
username = os.getenv("FTP_USER")  # Читаем имя пользователя из переменной окружения.
password = os.getenv("FTP_PASSWORD")  # Читаем пароль из переменной окружения.

if not host or not username or not password:  # Проверяем, что все обязательные параметры подключения заданы.
    raise ValueError("Не заданы FTP_HOST, FTP_USER или FTP_PASSWORD")  # Останавливаем программу с понятным сообщением.

ftp = FTP()  # Создаём объект FTP-клиента без немедленного подключения.

try:  # Начинаем блок безопасной работы с сетевым соединением.
    ftp.connect(host=host, port=21, timeout=10)  # Подключаемся к FTP-серверу через стандартный управляющий порт.
    ftp.login(user=username, passwd=password)  # Выполняем аутентификацию с полученными учётными данными.
    print("Текущий каталог:", ftp.pwd())  # Запрашиваем и выводим текущий удалённый каталог.
    ftp.retrlines("LIST")  # Запрашиваем у сервера список файлов и печатаем полученные строки.
finally:  # Выполняем завершающие действия независимо от успеха предыдущих операций.
    try:  # Начинаем дополнительный блок на случай, если соединение уже нарушено.
        ftp.quit()  # Корректно завершаем FTP-сессию командой QUIT.
    except all_errors:  # Обрабатываем стандартные FTP-ошибки при завершении повреждённого соединения.
        ftp.close()  # Принудительно закрываем локальное соединение без повторной сетевой команды.
```

В прикладном коде лучше перехватывать конкретные исключения `ftplib`, но сначала важно понять общую последовательность: подключение → вход → операция → закрытие.

## 7.6. Скачивание файла через FTP

```python
import os  # Импортируем os для чтения настроек из переменных окружения.
from pathlib import Path  # Импортируем Path для работы с локальными путями.
from ftplib import FTP  # Импортируем FTP-клиент.

host = os.getenv("FTP_HOST")  # Получаем адрес сервера.
username = os.getenv("FTP_USER")  # Получаем имя пользователя.
password = os.getenv("FTP_PASSWORD")  # Получаем пароль.
remote_file = "/reports/report.csv"  # Задаём путь к файлу на FTP-сервере.
local_file = Path("report.csv")  # Задаём имя локального файла.

if not host or not username or not password:  # Проверяем наличие параметров подключения.
    raise ValueError("Не заданы параметры FTP-подключения")  # Останавливаем выполнение при неполной конфигурации.

with FTP(host=host, timeout=10) as ftp:  # Подключаемся к серверу и обеспечиваем закрытие соединения после блока.
    ftp.login(user=username, passwd=password)  # Выполняем вход на сервер.
    with local_file.open("wb") as file_object:  # Открываем локальный файл в бинарном режиме для записи.
        ftp.retrbinary(f"RETR {remote_file}", file_object.write)  # Скачиваем удалённый файл частями и записываем байты локально.

print("Файл скачан:", local_file.resolve())  # Показываем полный путь к скачанному файлу.
```

Почему используется режим `wb`:

- `w` означает запись;
- `b` означает бинарный режим;
- бинарный режим подходит не только для изображений, но и для надёжной передачи любых файлов без преобразования байтов.

## 7.7. Загрузка файла на FTP-сервер

Загрузка возможна только при наличии разрешения на запись.

```python
import os  # Импортируем os для чтения переменных окружения.
from pathlib import Path  # Импортируем Path для работы с локальным файлом.
from ftplib import FTP  # Импортируем FTP-клиент.

host = os.getenv("FTP_HOST")  # Получаем адрес FTP-сервера.
username = os.getenv("FTP_USER")  # Получаем имя пользователя.
password = os.getenv("FTP_PASSWORD")  # Получаем пароль.
local_file = Path("report.csv")  # Указываем локальный файл для загрузки.
remote_name = "report.csv"  # Указываем имя файла на удалённом сервере.

if not host or not username or not password:  # Проверяем наличие параметров FTP-подключения.
    raise ValueError("Не заданы параметры FTP-подключения")  # Останавливаем программу при неполной конфигурации.

if not local_file.exists():  # Проверяем, существует ли локальный файл до сетевого подключения.
    raise FileNotFoundError(local_file)  # Останавливаем программу, если файл не найден.

with FTP(host=host, timeout=10) as ftp:  # Устанавливаем FTP-соединение и автоматически закрываем его после блока.
    ftp.login(user=username, passwd=password)  # Выполняем вход на сервер.
    with local_file.open("rb") as file_object:  # Открываем локальный файл в бинарном режиме для чтения.
        ftp.storbinary(f"STOR {remote_name}", file_object)  # Отправляем содержимое файла на сервер.

print("Файл отправлен на FTP-сервер.")  # Сообщаем о завершении операции без раскрытия секретов.
```

Перед загрузкой файлов нужно уточнить:

- в какой каталог разрешена запись;
- можно ли перезаписывать существующие файлы;
- требуется ли временное имя;
- есть ли ограничение размера;
- как проверить целостность результата;
- кто является владельцем переданных данных.

# 8. FTPS: FTP с TLS-защитой

FTPS использует модель FTP, но добавляет TLS-защиту соединения.

В Python для явного FTPS применяется класс `FTP_TLS`.

```python
import os  # Импортируем os для чтения переменных окружения.
import ssl  # Импортируем ssl для создания контекста проверки TLS-сертификата.
from ftplib import FTP_TLS  # Импортируем клиент FTP с TLS-защитой.

host = os.getenv("FTPS_HOST")  # Получаем адрес FTPS-сервера.
username = os.getenv("FTPS_USER")  # Получаем имя пользователя.
password = os.getenv("FTPS_PASSWORD")  # Получаем пароль.

if not host or not username or not password:  # Проверяем наличие всех параметров подключения.
    raise ValueError("Не заданы параметры FTPS-подключения")  # Останавливаем программу при неполной конфигурации.

secure_context = ssl.create_default_context()  # Создаём стандартный безопасный TLS-контекст с проверкой сертификатов.

with FTP_TLS(context=secure_context) as ftps:  # Создаём FTPS-клиент с настроенным TLS-контекстом.
    ftps.connect(host=host, port=21, timeout=10)  # Подключаемся к управляющему порту сервера.
    ftps.login(user=username, passwd=password)  # Выполняем аутентификацию пользователя.
    ftps.prot_p()  # Включаем защиту канала, по которому передаются файлы и списки каталогов.
    ftps.retrlines("LIST")  # Запрашиваем и выводим список файлов удалённого каталога.
```

Конкретные настройки FTPS зависят от сервера. Нельзя автоматически переносить параметры одного сервера на другой без документации владельца системы.

# 9. SSH: защищённое удалённое управление

## 9.1. Что такое SSH

**SSH — Secure Shell** — протокол защищённого удалённого доступа.

Через SSH можно:

- открыть терминальную сессию на сервере;
- выполнять команды;
- копировать файлы;
- создавать защищённые туннели;
- администрировать Linux-системы;
- автоматизировать ограниченные операции.

SSH обычно использует порт 22, но администратор может выбрать другой.

Упрощённая схема:

```text
локальный компьютер
        |
        | защищённое SSH-соединение
        v
удалённый сервер
        |
        | выполнение разрешённой команды
        v
результат
```

## 9.2. Аутентификация SSH

Распространены два способа:

1. логин и пароль;
2. пара криптографических ключей.

Для регулярной автоматизации обычно предпочтительнее ключи:

- закрытый ключ хранится у клиента;
- открытый ключ добавляется на сервер;
- закрытый ключ нельзя публиковать;
- доступ можно отозвать удалением открытого ключа на сервере.

## 9.3. Ключ сервера и ключ пользователя — разные вещи

Новички часто путают:

- **ключ пользователя** подтверждает право клиента войти;
- **host key сервера** помогает клиенту проверить, что он подключается к ожидаемому серверу.

Проверка host key защищает от подключения к подменённому серверу.

## 9.4. Установка Paramiko

Для SSH из Python можно использовать библиотеку `paramiko`.

```bash
# Устанавливаем библиотеку Paramiko в текущее Python-окружение.
python -m pip install paramiko
```

## 9.5. Выполнение команды через SSH

Пример ниже использует ключ пользователя и системный файл `known_hosts`. Не запускайте его без разрешённого сервера.

```python
import os  # Импортируем os для чтения настроек подключения из переменных окружения.
from pathlib import Path  # Импортируем Path для проверки файла закрытого ключа.
import paramiko  # Импортируем библиотеку Paramiko для работы с SSH.

host = os.getenv("SSH_HOST")  # Получаем адрес SSH-сервера из переменной окружения.
username = os.getenv("SSH_USER")  # Получаем имя пользователя SSH.
key_path = Path(os.getenv("SSH_KEY_PATH", "~/.ssh/id_ed25519")).expanduser()  # Получаем и разворачиваем путь к закрытому ключу.
command = "uname -a"  # Задаём безопасную диагностическую команду для разрешённого сервера.

if not host or not username:  # Проверяем наличие адреса сервера и имени пользователя.
    raise ValueError("Не заданы SSH_HOST или SSH_USER")  # Останавливаем программу при неполных настройках.

if not key_path.exists():  # Проверяем существование файла закрытого ключа.
    raise FileNotFoundError(key_path)  # Останавливаем программу, если ключ не найден.

client = paramiko.SSHClient()  # Создаём объект SSH-клиента.
client.load_system_host_keys()  # Загружаем известные ключи серверов из системного файла known_hosts.
client.set_missing_host_key_policy(paramiko.RejectPolicy())  # Запрещаем автоматическое доверие неизвестному ключу сервера.

try:  # Начинаем блок работы с SSH-соединением.
    client.connect(  # Начинаем вызов подключения к SSH-серверу.
        hostname=host,  # Передаём адрес удалённого сервера.
        port=22,  # Указываем стандартный SSH-порт.
        username=username,  # Передаём имя пользователя.
        key_filename=str(key_path),  # Передаём путь к закрытому ключу.
        timeout=10,  # Ограничиваем время установления TCP-соединения.
        auth_timeout=10,  # Ограничиваем время ожидания аутентификации.
    )  # Завершаем вызов подключения.
    stdin, stdout, stderr = client.exec_command(command, timeout=10)  # Выполняем удалённую команду и получаем три потока.
    output_text = stdout.read().decode("utf-8", errors="replace")  # Читаем стандартный вывод и преобразуем байты в текст.
    error_text = stderr.read().decode("utf-8", errors="replace")  # Читаем поток ошибок и преобразуем байты в текст.
    exit_code = stdout.channel.recv_exit_status()  # Получаем код завершения удалённой команды.
    print("Код завершения:", exit_code)  # Выводим код завершения команды.
    print("Стандартный вывод:", output_text)  # Выводим результат команды.
    print("Поток ошибок:", error_text)  # Выводим диагностические сообщения удалённой команды.
finally:  # Выполняем завершающее действие независимо от результата команды.
    client.close()  # Закрываем SSH-соединение и освобождаем сетевые ресурсы.
```

## 9.6. Почему не используется AutoAddPolicy

В демонстрационных примерах часто встречается:

```python
client.set_missing_host_key_policy(paramiko.AutoAddPolicy())  # Рискованный шаблон: автоматически доверяет неизвестному ключу сервера.
```

Для рабочего подключения безопаснее заранее получить и проверить ключ сервера, а затем использовать системный `known_hosts`. Автоматическое доверие неизвестному серверу ослабляет защиту от подмены.

## 9.7. Что делать, если сервер неизвестен known_hosts

Типовой безопасный процесс:

1. получить fingerprint ключа сервера у администратора по доверенному каналу;
2. проверить адрес сервера;
3. добавить проверенный ключ в `known_hosts`;
4. только после этого подключаться программно.

Нельзя считать сообщение «unknown host key» обычной помехой, которую всегда нужно отключать.

# 10. SFTP: передача файлов через SSH

## 10.1. Что такое SFTP

**SFTP — SSH File Transfer Protocol** — протокол передачи файлов, работающий внутри SSH-соединения.

SFTP и FTP — разные протоколы.

| Свойство | FTP | SFTP |
|---|---|---|
| базовая технология | FTP | SSH |
| типичный порт | 21 и дополнительные соединения | 22 |
| шифрование по умолчанию | нет | есть в рамках SSH |
| библиотека Python | `ftplib` | `paramiko` |
| аутентификация ключом | не классический сценарий FTP | распространена |

## 10.2. Просмотр файлов через SFTP

```python
import os  # Импортируем os для чтения параметров подключения.
from pathlib import Path  # Импортируем Path для работы с путём к закрытому ключу.
import paramiko  # Импортируем Paramiko для SSH- и SFTP-соединения.

host = os.getenv("SSH_HOST")  # Получаем адрес сервера.
username = os.getenv("SSH_USER")  # Получаем имя пользователя.
key_path = Path(os.getenv("SSH_KEY_PATH", "~/.ssh/id_ed25519")).expanduser()  # Получаем путь к закрытому ключу.
remote_directory = "/home/student/data"  # Задаём разрешённый каталог на удалённом сервере.

if not host or not username:  # Проверяем наличие адреса сервера и имени пользователя.
    raise ValueError("Не заданы SSH_HOST или SSH_USER")  # Останавливаем программу при неполной конфигурации.

if not key_path.exists():  # Проверяем наличие закрытого ключа до подключения.
    raise FileNotFoundError(key_path)  # Останавливаем программу, если ключ не найден.

client = paramiko.SSHClient()  # Создаём SSH-клиент.
client.load_system_host_keys()  # Загружаем доверенные ключи серверов.
client.set_missing_host_key_policy(paramiko.RejectPolicy())  # Запрещаем подключение к серверу с неизвестным ключом.

try:  # Начинаем блок работы с соединением.
    client.connect(  # Подключаемся к SSH-серверу.
        hostname=host,  # Передаём адрес сервера.
        username=username,  # Передаём имя пользователя.
        key_filename=str(key_path),  # Передаём путь к закрытому ключу.
        timeout=10,  # Ограничиваем время установления соединения.
    )  # Завершаем вызов подключения.
    sftp = client.open_sftp()  # Открываем SFTP-канал внутри SSH-соединения.
    try:  # Начинаем блок работы с SFTP-каналом.
        filenames = sftp.listdir(remote_directory)  # Получаем список имён файлов удалённого каталога.
        for filename in filenames:  # Перебираем полученные имена файлов.
            print(filename)  # Выводим каждое имя на отдельной строке.
    finally:  # Выполняем закрытие SFTP-канала независимо от результата операции.
        sftp.close()  # Закрываем SFTP-канал.
finally:  # Выполняем закрытие основного соединения независимо от результата.
    client.close()  # Закрываем SSH-соединение.
```

## 10.3. Скачивание файла через SFTP

```python
import os  # Импортируем os для чтения переменных окружения.
from pathlib import Path  # Импортируем Path для работы с локальными путями.
import paramiko  # Импортируем Paramiko для защищённого подключения.

username = os.getenv("SSH_USER")  # Получаем имя пользователя.
key_path = Path(os.getenv("SSH_KEY_PATH", "~/.ssh/id_ed25519")).expanduser()  # Получаем путь к закрытому ключу.
remote_file = "/home/student/data/report.csv"  # Задаём путь к удалённому файлу.
local_file = Path("report.csv")  # Задаём локальный путь для сохранения файла.

if not host or not username:  # Проверяем наличие адреса сервера и имени пользователя.
    raise ValueError("Не заданы SSH_HOST или SSH_USER")  # Останавливаем программу при неполной конфигурации.

if not key_path.exists():  # Проверяем наличие закрытого ключа до подключения.
    raise FileNotFoundError(key_path)  # Останавливаем программу, если ключ не найден.

client = paramiko.SSHClient()  # Создаём объект SSH-клиента.
client.load_system_host_keys()  # Загружаем проверенные host keys из known_hosts.
client.set_missing_host_key_policy(paramiko.RejectPolicy())  # Запрещаем автоматическое доверие неизвестному серверу.

try:  # Начинаем блок работы с SSH-соединением.
    client.connect(  # Устанавливаем защищённое соединение.
        hostname=host,  # Передаём адрес сервера.
        username=username,  # Передаём имя пользователя.
        key_filename=str(key_path),  # Передаём путь к закрытому ключу.
        timeout=10,  # Ограничиваем время установления соединения.
    )  # Завершаем вызов подключения.
    sftp = client.open_sftp()  # Открываем SFTP-канал.
    try:  # Начинаем блок передачи файла.
        sftp.get(remote_file, str(local_file))  # Скачиваем удалённый файл в локальный путь.
    finally:  # Гарантируем закрытие SFTP-канала.
        sftp.close()  # Закрываем SFTP-канал.
finally:  # Гарантируем закрытие SSH-соединения.
    client.close()  # Закрываем SSH-клиент.

print("Файл скачан:", local_file.resolve())  # Показываем полный путь к скачанному файлу.
```

# 11. Главное сравнение протоколов

| Критерий | HTTP | HTTPS | FTP | FTPS | SSH | SFTP |
|---|---|---|---|---|---|---|
| основная задача | обмен веб-ресурсами | защищённый обмен веб-ресурсами | передача файлов | защищённая передача через FTP | удалённое управление | передача файлов через SSH |
| типичный порт | 80 | 443 | 21 | зависит от режима и сервера | 22 | 22 |
| шифрование | нет | TLS | нет | TLS | есть | есть |
| Python-инструмент | `requests` | `requests` | `ftplib.FTP` | `ftplib.FTP_TLS` | `paramiko` | `paramiko` |
| типичный сценарий | открытая страница | сайт или API | старый файловый обмен | защищённый FTP-сервис | команды на сервере | защищённый обмен файлами |

Короткая формула:

```text
HTTP/HTTPS — запросить ресурс или передать данные веб-сервису.
FTP/FTPS — работать с файлами на FTP-сервере.
SSH — выполнить разрешённую команду на удалённом сервере.
SFTP — передать файл через SSH.
```

# 13. Типовые ошибки HTTP и HTTPS

## 13.1. Ошибка DNS

Признак:

```text
NameResolutionError
Temporary failure in name resolution
```

Такая ошибка возникает до отправки HTTP-запроса: программа не получила пригодный адрес по доменному имени.

Проверьте:

- написание домена;
- подключение к сети;
- корпоративный VPN;
- используемый DNS-сервер;
- локальный файл `hosts`;
- наличие A- или AAAA-записи;
- TTL и возможный отрицательный кэш;
- доступность домена из требуемой сети.

Не отключайте проверку TLS-сертификата и не заменяйте домен случайным IP-адресом: это не устраняет причину DNS-ошибки. Подробный порядок диагностики приведён в разделе 2.30.

## 13.2. Connection refused

Сервер найден, но соединение на указанном порту не принято.

Возможные причины:

- служба не запущена;
- указан неправильный порт;
- межсетевой экран блокирует подключение;
- сервер принимает подключения только из внутренней сети.

## 13.3. Timeout

Сервер не ответил в ожидаемое время.

Возможные причины:

- медленная сеть;
- сервер перегружен;
- порт фильтруется;
- слишком маленькое значение timeout;
- сервер действительно недоступен.

Нельзя бесконечно увеличивать timeout, не выяснив причину.

## 13.4. 401 Unauthorized

Обычно означает, что сервер требует аутентификацию или переданные данные аутентификации не подходят.

## 13.5. 403 Forbidden

Сервер понял запрос, но отказывает в доступе. Пользователь может быть аутентифицирован, но не иметь нужного права.

## 13.6. 404 Not Found

Ресурс не найден по указанному пути. Нужно проверить URL и документацию сервиса.

## 13.7. 500 или 503

Проблема возникла на стороне сервера. Клиент должен корректно зафиксировать ошибку. Повтор запроса допустим не всегда: важно учитывать тип операции и риск повторного создания данных.

## 13.8. Ошибка TLS-сертификата

Возможные причины:

- сертификат истёк;
- домен не соответствует сертификату;
- используется корпоративный сертификат, которому среда Python не доверяет;
- системное время настроено неправильно;
- соединение перехватывается защитным шлюзом организации.

Правильное действие — проверить сертификат и доверенную цепочку, а не автоматически отключать проверку.

# 14. Типовые ошибки FTP, SSH и SFTP

## 14.1. Authentication failed

Проверьте:

- имя пользователя;
- пароль или ключ;
- разрешённый способ аутентификации;
- срок действия учётной записи;
- права пользователя;
- правильность сервера.

## 14.2. Permission denied

Подключение успешно, но операция запрещена.

Например:

- нельзя войти в каталог;
- нельзя скачать файл;
- нельзя создать файл;
- нельзя выполнить команду.

Не следует обходить ограничение. Нужно запросить правильные права у владельца системы.

## 14.3. No such file

Удалённый путь неверен или файл был перемещён. Путь Linux чувствителен к регистру символов.

## 14.4. Unknown host key

SSH-клиент ещё не знает ключ сервера. Нужно сверить fingerprint с администратором и добавить проверенный ключ в `known_hosts`.

## 14.5. Host key has changed

Это критически важное предупреждение. Возможны:

- переустановка сервера;
- законная замена ключей;
- обращение к другому серверу по тому же адресу;
- ошибка DNS;
- попытка подмены.

Нельзя просто удалять старый ключ без проверки причины.

## 14.6. FTP работает локально, но не работает через корпоративную сеть

FTP использует отдельные соединения для команд и данных, поэтому может конфликтовать с NAT и межсетевыми экранами. Нужно проверить пассивный режим, разрешённые порты и правила сетевой безопасности.

# 15. Требования безопасности

## 15.1. Не храните секреты в коде

Нельзя публиковать:

- пароли;
- закрытые SSH-ключи;
- API-токены;
- cookie сессии;
- приватные адреса и внутренние данные без необходимости.

Используйте:

- переменные окружения;
- менеджер секретов;
- защищённые настройки CI/CD;
- локальный файл `.env`, исключённый из Git, только в допустимых сценариях;
- минимальные права учётной записи.

## 15.2. Не отключайте проверку сертификата

`verify=False` не является обычным способом «исправить HTTPS». Это отключение важной проверки.

## 15.3. Проверяйте host key SSH

Не доверяйте неизвестному серверу автоматически в production-сценариях.

## 15.4. Ограничивайте время ожидания

Для сетевых операций задавайте timeout, чтобы программа не зависала бесконечно.

## 15.5. Закрывайте соединения

Используйте:

- контекстные менеджеры `with`, если библиотека их поддерживает;
- `try/finally` для гарантированного закрытия;
- явные вызовы `close()`.

## 15.6. Применяйте минимальные права

Пользователь для скачивания файла не должен автоматически получать права администратора сервера.

## 15.7. Проверяйте полученный файл

Для важных процессов проверяйте:

- размер;
- ожидаемое имя;
- формат;
- контрольную сумму, если она предоставлена;
- количество строк для табличных данных;
- дату обновления;
- отсутствие неожиданного исполняемого содержимого.

# 16. Пример мини-проекта: безопасно получить страницу по HTTPS

## Задача

Нужно получить страницу, сохранить её локально и записать короткий отчёт о результате.

## Вход

- HTTPS-адрес;
- путь к выходному файлу.

## Выход

- сохранённый HTML-файл;
- статус ответа;
- тип содержимого;
- размер файла.

## Код

```python
from pathlib import Path  # Импортируем Path для работы с локальным файлом.
import requests  # Импортируем requests для HTTPS-запроса.

url = "https://example.com"  # Задаём адрес ресурса.
output_file = Path("example_page.html")  # Задаём путь сохранения страницы.

try:  # Начинаем блок обработки ожидаемых сетевых ошибок.
    response = requests.get(url, timeout=10)  # Получаем ресурс с ограничением времени ожидания.
    response.raise_for_status()  # Проверяем, что HTTP-статус не относится к ошибочным 4xx или 5xx.
    content_type = response.headers.get("Content-Type", "не указан")  # Читаем тип содержимого или используем понятное значение по умолчанию.
    output_file.write_bytes(response.content)  # Сохраняем тело ответа как последовательность байтов.
    file_size = output_file.stat().st_size  # Получаем фактический размер созданного файла.
    print("Результат: успешно")  # Выводим общий статус операции.
    print("HTTP-статус:", response.status_code)  # Выводим статус ответа сервера.
    print("Тип содержимого:", content_type)  # Выводим тип полученных данных.
    print("Файл:", output_file.resolve())  # Выводим полный путь к результату.
    print("Размер:", file_size, "байт")  # Выводим размер сохранённого файла.
except requests.exceptions.Timeout:  # Обрабатываем превышение времени ожидания.
    print("Результат: сервер не ответил вовремя")  # Сообщаем о timeout понятным языком.
except requests.exceptions.ConnectionError:  # Обрабатываем ошибку DNS или подключения.
    print("Результат: соединение не установлено")  # Сообщаем о проблеме соединения.
except requests.exceptions.HTTPError as error:  # Обрабатываем ошибочный HTTP-статус.
    print("Результат: HTTP-ошибка", error)  # Показываем полученную HTTP-ошибку.
except OSError as error:  # Обрабатываем ошибку записи локального файла.
    print("Результат: файл не сохранён", error)  # Показываем проблему файловой системы.
except requests.exceptions.RequestException as error:  # Обрабатываем остальные ошибки библиотеки requests.
    print("Результат: ошибка запроса", error)  # Показываем описание непредвиденной ошибки запроса.
```

## Как проверить результат

1. код завершился без traceback;
2. статус находится в успешной группе 2xx;
3. файл появился в рабочей папке;
4. размер файла больше нуля;
5. файл открывается как HTML;
6. секреты не записаны в код;
7. используется HTTPS;
8. задан timeout.

# 19. Краткая памятка

```text
DNS
Находит сетевые и служебные данные по доменному имени.

HTTP
Правила обмена веб-запросами и ответами.

HTTPS
HTTP через защищённое TLS-соединение.

FTP
Классическая передача файлов без современной защиты по умолчанию.

FTPS
FTP с TLS-защитой.

SSH
Защищённое удалённое управление сервером.

SFTP
Защищённая передача файлов внутри SSH.
```

Базовый выбор:

```text
доменное имя в IP       → DNS
веб-ресурс или API      → HTTPS
старый файловый сервер  → FTP или FTPS по требованиям системы
защищённая передача     → SFTP
удалённая команда       → SSH
```

# 20. Типовые ошибки новичка

1. Считать интернет и HTTP одним и тем же.
2. Считать HTTPS отдельным форматом данных.
3. Не проверять статус ответа.
4. Не задавать timeout.
5. Использовать `verify=False` как постоянное решение.
6. Публиковать пароль в коде или Git.
7. Путать FTP, FTPS и SFTP.
8. Автоматически принимать неизвестный SSH host key.
9. Выполнять команды на production-сервере без разрешения.
10. Не закрывать сетевое соединение.
11. Считать статус 200 гарантией правильности содержимого.
12. Не проверять размер и формат скачанного файла.
13. Повторять изменяющий запрос после ошибки, не понимая последствия.

15. Использовать административную учётную запись для простой загрузки файла.

# 21. Итог

DNS, HTTP, HTTPS, FTP, FTPS, SSH и SFTP относятся к сетевому взаимодействию, но решают разные задачи.

- DNS помогает преобразовать доменные имена в адреса и получить служебные записи.
- HTTP описывает обмен запросами и ответами.
- HTTPS защищает HTTP-соединение с помощью TLS.
- FTP предназначен для передачи файлов, но обычный FTP не обеспечивает современную защиту данных.
- FTPS добавляет TLS к FTP.
- SSH предоставляет защищённый удалённый доступ.
- SFTP передаёт файлы внутри SSH-соединения.

Для начинающего специалиста важнее всего освоить следующую последовательность:

```text
клиент и сервер
→ адрес и URL
→ DNS и разрешение имени
→ запрос и ответ
→ HTTP
→ HTTPS
→ безопасный Python-запрос
→ передача файлов
→ SSH и SFTP
→ обработка ошибок
→ требования безопасности
```

Следующий логический шаг — изучение API и REST API: endpoints, HTTP-методов, параметров, headers, JSON, авторизации, статусных кодов и обработки ошибок программного интерфейса.
