# API и REST API: от первого запроса до надёжной интеграции на Python

## Для чего нужен этот материал

Программы часто должны получать данные друг от друга. Интернет-магазин запрашивает остатки товара, мобильное приложение получает список заказов, аналитический скрипт загружает статистику, а корпоративная система передаёт сведения в другой сервис.

Для такого взаимодействия используют **API** — программный интерфейс, который описывает, какие операции доступны, какие данные нужно передать и какой ответ можно получить.

В этом материале последовательно разбираются:

- понятие API;
- отличие API от сайта и пользовательского интерфейса;
- назначение web API;
- архитектурный стиль REST;
- ресурсы, endpoint и URL;
- методы HTTP;
- path parameters и query parameters;
- headers и body;
- формат JSON;
- коды ответа HTTP;
- аутентификация и авторизация;
- API-ключи и bearer-токены;
- обработка ошибок;
- тайм-ауты и повторные попытки;
- пагинация;
- ограничения частоты запросов;
- идемпотентность;
- версионирование;
- загрузка данных API в `pandas`;
- сохранение результата в CSV;
- базовый контроль качества интеграции.

После изучения материала вы сможете:

1. объяснить, что такое API и зачем оно нужно;
2. отличить API от сайта, базы данных и протокола HTTP;
3. прочитать адрес endpoint;
4. выбрать подходящий HTTP-метод;
5. передать параметры, заголовки и JSON-тело;
6. обработать успешный и ошибочный ответ;
7. безопасно использовать токен из переменной окружения;
8. получить несколько страниц данных;
9. загрузить ответ API в `pandas`;
10. сформировать воспроизводимый Python-скрипт для интеграции.

> Примеры с внешними сервисами предназначены для изучения структуры запросов. Доступность публичного тестового API, состав его данных и ограничения могут измениться. Перед использованием реального API всегда изучайте его официальную документацию.

# 1. Что такое интерфейс

## 1.1. Интерфейс как точка взаимодействия

**Интерфейс** — это согласованный способ взаимодействия между двумя сторонами.

Примеры интерфейсов:

- кнопки и формы сайта — интерфейс между человеком и программой;
- функции библиотеки Python — интерфейс между программным кодом и библиотекой;
- команды операционной системы — интерфейс между пользователем или программой и системой;
- API — интерфейс между программами.

Интерфейс описывает не внутреннее устройство системы, а доступный способ работы с ней.

Например, пользователю банкомата не нужно знать, как устроена банковская база данных. Ему достаточно знать доступные операции:

- вставить карту;
- ввести PIN-код;
- запросить баланс;
- снять деньги;
- получить результат операции.

API действует похожим образом: оно скрывает внутреннюю реализацию системы и предоставляет согласованный набор операций.

## 1.2. Определение API

**API — Application Programming Interface**, программный интерфейс приложения.

API определяет:

- какие операции доступны;
- по какому адресу к ним обращаться;
- какие параметры обязательны;
- в каком формате отправлять данные;
- как подтвердить права доступа;
- какой ответ возвращает система;
- какие ошибки возможны;
- какие ограничения действуют.

Упрощённая схема:

```text
программа-клиент
      |
      | запрос по правилам API
      v
система или сервис
      |
      | ответ по правилам API
      v
программа-клиент
```

## 1.3. API — это не обязательно интернет

API бывает разным.

### API библиотеки

Когда программа вызывает функцию:

```python
result = len([10, 20, 30])  # Вызываем встроенную функцию len через программный интерфейс Python.
```

она использует API языка Python.

### API операционной системы

Когда Python открывает файл, он использует возможности операционной системы через программный интерфейс.

### API базы данных

Программа может отправлять SQL-запрос драйверу базы данных.

### Web API

Программа обращается к удалённому серверу через HTTP или HTTPS.

В этом материале основной акцент сделан на **web API**, потому что именно с ним часто работают аналитики, системные аналитики и разработчики интеграций.

# 2. API, сайт, сервер и база данных — не одно и то же

## 2.1. Сайт предназначен прежде всего для человека

Обычная веб-страница возвращает HTML, CSS, JavaScript, изображения и другие материалы, которые браузер превращает в пользовательский интерфейс.

```text
человек → браузер → сайт → HTML → визуальная страница
```

Пользователь нажимает кнопки, заполняет формы и читает текст.

## 2.2. API предназначено для программы

API обычно возвращает структурированные данные, которые удобно обрабатывать программно.

```text
Python-скрипт → HTTPS → API → JSON → Python-объект
```

Вместо красивой страницы программа получает, например, такой ответ:

```json
{
  "order_id": 501,
  "status": "paid",
  "amount": 3490.0
}
```

## 2.3. Один сервер может обслуживать сайт и API

Например:

```text
https://shop.example.com/             — сайт для человека
https://api.example.com/v1/orders     — API для программ
```

Это могут быть:

- разные приложения;
- разные домены;
- разные серверы;
- разные части одной системы.

## 2.4. API не является базой данных

API может получать данные из базы данных, но клиент не обязан знать внутреннюю схему хранения.

```text
клиент
  ↓ API-запрос
сервер приложения
  ↓ внутренний запрос
база данных
  ↓ результат
сервер приложения
  ↓ API-ответ
клиент
```

API может:

- проверить права пользователя;
- проверить входные данные;
- применить бизнес-правила;
- объединить сведения из нескольких систем;
- скрыть внутренние поля;
- зарегистрировать операцию в журнале;
- вернуть только разрешённые данные.

Поэтому API нельзя рассматривать как прямой доступ к таблице базы данных.

# 3. Что такое web API

**Web API** — API, доступное через сетевые протоколы веба, чаще всего через HTTPS.

Клиент формирует HTTP-запрос, а сервер возвращает HTTP-ответ.

Пример логики:

```text
GET /api/v1/orders/501 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer <token>
```

Ответ:

```text
HTTP/1.1 200 OK
Content-Type: application/json
```

Тело ответа:

```json
{
  "order_id": 501,
  "status": "paid",
  "amount": 3490.0
}
```

Web API использует HTTP как транспорт и набор стандартных семантик:

- метод запроса;
- адрес ресурса;
- заголовки;
- тело запроса;
- код состояния;
- заголовки ответа;
- тело ответа.

# 4. Что такое REST

## 4.1. REST — не отдельный сетевой протокол

**REST — Representational State Transfer** — архитектурный стиль проектирования распределённых систем.

REST не заменяет HTTP. Практические REST API обычно используют HTTP или HTTPS и опираются на его методы, адреса, заголовки и коды ответа.

Некорректная формулировка:

> REST — это протокол передачи данных.

Более точная формулировка:

> REST — архитектурный стиль, по принципам которого может быть спроектирован web API.

## 4.2. Главная идея: работа с ресурсами

В REST система представляется как набор **ресурсов**.

Примеры ресурсов:

- пользователь;
- заказ;
- товар;
- платёж;
- обращение в поддержку;
- документ;
- отчёт.

Ресурс получает адрес:

```text
/api/v1/orders/501
```

Здесь клиент обращается к заказу с идентификатором `501`.

## 4.3. Представление ресурса

Клиент обычно получает не сам внутренний объект системы, а его **представление**.

Например, заказ может быть представлен в JSON:

```json
{
  "id": 501,
  "status": "paid",
  "amount": 3490.0
}
```

Другой клиент теоретически может получить представление в XML или ином формате, если API это поддерживает.

REST не требует использовать только JSON. JSON просто стал распространённым форматом web API.

## 4.4. Основные ограничения REST простыми словами

### Разделение клиента и сервера

Клиент отвечает за свой интерфейс и отправку запросов. Сервер отвечает за данные, правила и обработку операций.

### Stateless — отсутствие скрытого состояния диалога

Каждый запрос должен содержать сведения, необходимые для его обработки. Сервер не должен требовать, чтобы клиент сначала выполнил неизвестную последовательность запросов, от которой скрыто зависит текущая операция.

Это не означает, что сервер ничего не хранит. Сервер хранит пользователей, заказы, документы и другие данные. Ограничение относится к скрытому состоянию взаимодействия между запросами.

### Кэшируемость

Ответ должен позволять определить, можно ли использовать его повторно из кэша.

### Единообразный интерфейс

Ресурсы идентифицируются адресами, а операции выражаются через согласованные методы и представления.

### Слои

Между клиентом и конечным сервером могут находиться прокси, шлюзы, балансировщики, кэши и другие промежуточные компоненты.

### Code on Demand

Необязательное ограничение: сервер может передавать клиенту исполняемый код. Для большинства базовых REST API этот аспект не является центральным.

## 4.5. Почему не каждое HTTP API полностью соответствует REST

На практике термином REST API часто называют HTTP API, которое:

- использует URL ресурсов;
- использует стандартные методы HTTP;
- возвращает JSON;
- не хранит скрытое состояние сессии между запросами.

При этом некоторые строгие ограничения REST, особенно гипермедиа, могут быть реализованы частично или не реализованы. Поэтому в документации встречаются формулировки:

- REST API;
- RESTful API;
- HTTP API;
- JSON API.

Для начинающего специалиста важнее не название, а фактический контракт: методы, адреса, схемы данных, ошибки, права и ограничения.

## 4.6. REST — не единственный способ проектировать API

Кроме REST-подобных HTTP API существуют другие подходы:

- **SOAP** — протокол обмена структурированными сообщениями, часто с XML и формальными контрактами;
- **GraphQL** — подход, при котором клиент формирует запрос к схеме и выбирает нужные поля;
- **RPC** — вызов удалённой операции так, будто это функция;
- **gRPC** — RPC-подход с формальным контрактом Protocol Buffers и поддержкой разных языков;
- **событийные интерфейсы** — обмен событиями через брокеры сообщений, а не только синхронные HTTP-запросы.

REST не является автоматически лучшим вариантом для любой системы. Выбор зависит от требований к контракту, задержке, объёму данных, потоковой передаче, совместимости и инфраструктуре. В этой части подробно рассматривается REST API, потому что он широко применяется и хорошо демонстрирует базовую логику HTTP-интеграций.

# 5. Producer, consumer, client и server

В интеграциях полезно различать роли.

- **Producer** — система, которая предоставляет или создаёт данные.
- **Consumer** — система, которая использует данные.
- **Client** — сторона, которая инициирует HTTP-запрос.
- **Server** — сторона, которая принимает запрос и формирует ответ.

В простом запросе клиент часто является consumer, а сервер — producer. Но роли могут меняться в разных операциях.

Пример:

```text
аналитический скрипт              CRM
consumer / HTTP client   →   producer / HTTP server
```

Если CRM вызывает webhook аналитической платформы, направление меняется:

```text
CRM                              аналитическая платформа
producer / HTTP client   →   consumer / HTTP server
```

Поэтому при описании интеграции нужно явно указать:

- кто инициирует запрос;
- кто предоставляет данные;
- кто является владельцем данных;
- кто отвечает за ошибку;
- какой результат ожидает consumer.

# 6. Endpoint

## 6.1. Определение endpoint

**Endpoint** — конкретная точка API, доступная по сочетанию HTTP-метода и адреса.

Например:

```text
GET https://api.example.com/v1/orders/501
```

Endpoint определяется не только URL, но и методом.

Следующие операции могут иметь одинаковый URL, но разный смысл:

```text
GET    /v1/orders/501   — получить заказ
PUT    /v1/orders/501   — полностью заменить представление заказа
PATCH  /v1/orders/501   — частично изменить заказ
DELETE /v1/orders/501   — удалить заказ
```

## 6.2. Из чего состоит URL API

Пример:

```text
https://api.example.com/v1/orders/501?include=items
```

| Часть | Значение | Смысл |
|---|---|---|
| схема | `https` | защищённое HTTP-соединение |
| хост | `api.example.com` | сервер API |
| версия | `/v1` | версия контракта, если используется URL-версионирование |
| коллекция | `/orders` | набор заказов |
| идентификатор | `/501` | конкретный заказ |
| query parameter | `include=items` | дополнительная настройка ответа |

## 6.3. Коллекция и отдельный ресурс

```text
GET /v1/orders       — получить коллекцию заказов
GET /v1/orders/501   — получить один заказ
```

Для адресов ресурсов обычно используют существительные:

```text
/orders
/users
/products
```

Менее REST-подобный вариант:

```text
/getOrders
/createOrder
/deleteOrder
```

Однако реальный контракт определяет владелец API. Клиент должен соблюдать документацию, а не самостоятельно переименовывать endpoint.

## 6.4. Вложенные ресурсы

Пример:

```text
GET /v1/orders/501/items
```

Такой endpoint может означать получение позиций заказа `501`.

Слишком глубокая вложенность усложняет API:

```text
/v1/customers/17/orders/501/items/3/discounts/2
```

При проектировании API нужно проверять, действительно ли вся иерархия нужна в URL.

# 7. HTTP-методы в API

## 7.1. GET — получить данные

`GET` используется для чтения представления ресурса.

Примеры:

```text
GET /v1/products
GET /v1/products/42
```

`GET` не должен использоваться для намеренного изменения состояния системы.

## 7.2. POST — создать ресурс или запустить операцию

Часто `POST` используется для создания ресурса:

```text
POST /v1/orders
```

Тело запроса может содержать данные нового заказа.

`POST` также может использоваться для операции, которая не укладывается в простое создание ресурса. Точный смысл определяется контрактом API.

## 7.3. PUT — полностью заменить ресурс по известному адресу

Пример:

```text
PUT /v1/users/42
```

Обычно клиент передаёт полное новое представление ресурса. Если поле пропущено, сервер может удалить его, оставить без изменения или отклонить запрос — это зависит от документации.

## 7.4. PATCH — частично изменить ресурс

Пример:

```text
PATCH /v1/users/42
```

Клиент передаёт только изменяемые поля.

Формат patch-документа должен быть определён документацией. Нельзя предполагать, что любое API понимает произвольный JSON для `PATCH`.

## 7.5. DELETE — удалить ресурс

Пример:

```text
DELETE /v1/orders/501
```

Удаление может быть:

- физическим;
- логическим;
- отложенным;
- запрещённым для некоторых статусов.

Это определяется бизнес-правилами системы.

## 7.6. HEAD — получить заголовки без тела

`HEAD` похож на `GET`, но сервер обычно не возвращает тело ответа.

Его можно использовать, чтобы проверить:

- существует ли ресурс;
- размер файла;
- дату изменения;
- тип содержимого.

## 7.7. OPTIONS — узнать поддерживаемые возможности

`OPTIONS` может использоваться для получения сведений о доступных методах или настройках взаимодействия. Реальная поддержка зависит от сервера.

## 7.8. Краткая таблица методов

| Метод | Типичное назначение | Безопасный | Идемпотентный по семантике HTTP |
|---|---|---:|---:|
| GET | получить данные | да | да |
| HEAD | получить заголовки | да | да |
| POST | создать или запустить операцию | нет | обычно нет |
| PUT | полностью заменить ресурс | нет | да |
| PATCH | частично изменить ресурс | нет | не гарантируется |
| DELETE | удалить ресурс | нет | да |
| OPTIONS | узнать возможности | да | да |

**Безопасный метод** не должен намеренно изменять состояние ресурса.

**Идемпотентный метод** при повторении одинакового запроса должен иметь тот же ожидаемый эффект на сервере, что и один запрос. Ответы при этом могут различаться.

Например, второй `DELETE` может вернуть `404`, но ресурс уже отсутствует, поэтому итоговое состояние остаётся тем же.

# 8. Первый GET-запрос на Python

## 8.1. Установка Requests

Библиотека `requests` не входит в стандартную библиотеку Python. Её нужно установить:

```bash
python -m pip install requests  # Устанавливаем библиотеку requests в текущее окружение Python.
```

Проверить установку:

```bash
python -m pip show requests  # Показываем сведения об установленной библиотеке requests.
```

## 8.2. Простой запрос

В примерах используется публичный тестовый сервис JSONPlaceholder. Он имитирует REST API. Операции изменения данных могут возвращать успешный ответ, но изменения не обязаны сохраняться постоянно.

```python
import requests  # Импортируем библиотеку requests для выполнения HTTP-запросов.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Сохраняем адрес тестового ресурса в переменную.
response = requests.get(url, timeout=10)  # Отправляем GET-запрос и ограничиваем ожидание ответа десятью секундами.

print("Код ответа:", response.status_code)  # Выводим числовой HTTP-код, который вернул сервер.
print("Тип ответа:", response.headers.get("Content-Type"))  # Получаем тип содержимого из заголовков ответа.
print("Текст ответа:", response.text)  # Показываем тело ответа как обычный текст.
```

## 8.3. Проверка успешности

```python
import requests  # Импортируем библиотеку requests для выполнения HTTP-запросов.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Указываем адрес тестового ресурса.
response = requests.get(url, timeout=10)  # Отправляем GET-запрос с тайм-аутом.
response.raise_for_status()  # Создаём исключение HTTPError, если сервер вернул ошибочный статус.

data = response.json()  # Преобразуем JSON-тело ответа в объект Python.

print("Идентификатор:", data["id"])  # Выводим значение поля id из полученного словаря.
print("Заголовок:", data["title"])  # Выводим значение поля title из полученного словаря.
```

Важно различать две проверки:

1. `raise_for_status()` проверяет HTTP-статус;
2. `response.json()` пытается разобрать тело как JSON.

Успешный разбор JSON не означает, что запрос был успешным: сервер может вернуть описание ошибки в JSON вместе со статусом `400` или `500`.

Если сервер вернул `204 No Content`, тело ответа отсутствует. В таком случае не следует вызывать `response.json()`: попытка разобрать пустое тело завершится ошибкой декодирования JSON.

# 9. Объект Response

После запроса `requests` возвращает объект `Response`.

Полезные свойства и методы:

| Элемент | Назначение |
|---|---|
| `response.status_code` | числовой код ответа |
| `response.ok` | `True` для статусов меньше 400 |
| `response.headers` | заголовки ответа |
| `response.text` | тело как строка |
| `response.content` | тело как байты |
| `response.json()` | попытка разобрать JSON |
| `response.url` | итоговый URL запроса |
| `response.elapsed` | время до получения ответа |
| `response.raise_for_status()` | исключение при ошибочном HTTP-статусе |

Пример диагностики:

```python
import requests  # Импортируем библиотеку requests.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Задаём URL тестового ресурса.
response = requests.get(url, timeout=10)  # Выполняем запрос с ограничением времени ожидания.

print("Запрошенный URL:", response.url)  # Показываем итоговый адрес с учётом параметров и перенаправлений.
print("Код:", response.status_code)  # Показываем HTTP-код ответа.
print("Успешность:", response.ok)  # Показываем упрощённый логический признак успешности.
print("Время ответа:", response.elapsed.total_seconds())  # Переводим время ответа в секунды.
print("Заголовки:", dict(response.headers))  # Преобразуем заголовки ответа в обычный словарь для просмотра.
```

`response.ok` удобен для быстрой проверки, но в рабочем коде лучше проверять ожидаемые коды и использовать `raise_for_status()`.

# 10. JSON

## 10.1. Что такое JSON

**JSON — JavaScript Object Notation** — текстовый формат представления структурированных данных.

JSON поддерживает:

- объект;
- массив;
- строку;
- число;
- `true`;
- `false`;
- `null`.

Пример объекта:

```json
{
  "id": 501,
  "status": "paid",
  "amount": 3490.0,
  "active": true,
  "comment": null
}
```

Пример массива:

```json
[
  {
    "id": 501,
    "status": "paid"
  },
  {
    "id": 502,
    "status": "created"
  }
]
```

## 10.2. JSON и объекты Python

| JSON | Python после разбора |
|---|---|
| object | `dict` |
| array | `list` |
| string | `str` |
| number | `int` или `float` |
| true | `True` |
| false | `False` |
| null | `None` |

## 10.3. JSON — это не словарь Python

В JSON:

- строки и имена полей используют двойные кавычки;
- логические значения пишутся `true` и `false`;
- пустое значение пишется `null`;
- комментарии стандартным JSON не поддерживаются.

В Python:

```python
python_data = {  # Создаём словарь Python.
    "active": True,  # Используем Python-значение True с заглавной буквы.
    "comment": None,  # Используем Python-значение None вместо JSON null.
}  # Завершаем словарь Python.
```

## 10.4. Преобразование Python-объекта в JSON-строку

```python
import json  # Импортируем стандартный модуль json для преобразования данных.

python_data = {  # Создаём словарь Python с данными заказа.
    "order_id": 501,  # Добавляем числовой идентификатор заказа.
    "status": "paid",  # Добавляем строковый статус заказа.
    "active": True,  # Добавляем логическое значение Python.
}  # Завершаем создание словаря.

json_text = json.dumps(python_data, ensure_ascii=False, indent=2)  # Преобразуем словарь в форматированную JSON-строку.

print(json_text)  # Выводим полученную JSON-строку.
```

## 10.5. Преобразование JSON-строки в Python

```python
import json  # Импортируем стандартный модуль json.

json_text = '{"order_id": 501, "status": "paid", "active": true}'  # Сохраняем корректную JSON-строку.
python_data = json.loads(json_text)  # Преобразуем JSON-строку в словарь Python.

print(type(python_data))  # Показываем тип полученного объекта Python.
print(python_data["status"])  # Получаем значение поля status из словаря.
```

# 11. Path parameters и query parameters

## 11.1. Path parameter

Параметр пути обычно идентифицирует конкретный ресурс.

```text
GET /v1/orders/501
```

Здесь `501` — path parameter.

В документации шаблон может выглядеть так:

```text
GET /v1/orders/{order_id}
```

Фигурные скобки обозначают место, куда клиент подставляет значение.

## 11.2. Query parameters

Query parameters передаются после `?`.

```text
GET /v1/orders?status=paid&limit=50
```

Они часто используются для:

- фильтрации;
- сортировки;
- пагинации;
- выбора полей;
- поиска;
- изменения детализации ответа.

## 11.3. Передача query parameters через Requests

Не следует собирать строку параметров вручную, если библиотека может сделать это безопасно.

```python
import requests  # Импортируем библиотеку requests.

url = "https://jsonplaceholder.typicode.com/posts"  # Указываем endpoint коллекции публикаций.
params = {  # Создаём словарь query parameters.
    "userId": 1,  # Просим вернуть публикации пользователя с идентификатором 1.
}  # Завершаем словарь параметров.

response = requests.get(url, params=params, timeout=10)  # Передаём параметры через аргумент params и выполняем GET-запрос.
response.raise_for_status()  # Проверяем успешность HTTP-ответа.

posts = response.json()  # Преобразуем JSON-массив в список объектов Python.

print("Итоговый URL:", response.url)  # Показываем URL, который сформировала библиотека requests.
print("Количество объектов:", len(posts))  # Выводим число полученных публикаций.
print("Первый объект:", posts[0])  # Показываем первый элемент списка.
```

## 11.4. Параметр пути формируется отдельно

```python
import requests  # Импортируем библиотеку requests.

post_id = 1  # Сохраняем идентификатор требуемой публикации.
url = f"https://jsonplaceholder.typicode.com/posts/{post_id}"  # Подставляем идентификатор в путь endpoint.

response = requests.get(url, timeout=10)  # Отправляем GET-запрос к конкретному ресурсу.
response.raise_for_status()  # Проверяем HTTP-статус ответа.

post = response.json()  # Преобразуем JSON-объект ответа в словарь Python.
print(post)  # Показываем полученный объект.
```

Значения, полученные от пользователя, нельзя без проверки произвольно подставлять в URL. Нужно учитывать ожидаемый тип, допустимый диапазон и правила API.

# 12. Headers

## 12.1. Что такое заголовки

HTTP-заголовки передают метаданные запроса или ответа.

Заголовки запроса могут сообщать:

- какой формат ответа ожидает клиент;
- в каком формате отправлено тело;
- какой токен используется;
- язык ответа;
- идентификатор запроса;
- версию клиента.

## 12.2. Часто используемые заголовки

| Заголовок | Назначение |
|---|---|
| `Accept` | какой формат ответа ожидает клиент |
| `Content-Type` | формат тела запроса или ответа |
| `Authorization` | данные аутентификации или токен |
| `User-Agent` | сведения о клиентской программе |
| `If-None-Match` | условный запрос с ETag |
| `Retry-After` | когда можно повторить запрос |
| `X-Request-ID` | пример пользовательского идентификатора запроса; конкретное имя зависит от системы |

## 12.3. Accept и Content-Type — разные заголовки

```text
Accept: application/json
```

означает:

> Клиент хотел бы получить JSON.

```text
Content-Type: application/json
```

означает:

> Тело этого сообщения содержит JSON.

## 12.4. Отправка пользовательских заголовков

```python
import requests  # Импортируем библиотеку requests.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Указываем адрес тестового ресурса.
headers = {  # Создаём словарь HTTP-заголовков.
    "Accept": "application/json",  # Сообщаем серверу, что ожидаем ответ в JSON.
    "User-Agent": "beginner-api-client/1.0",  # Указываем понятное имя демонстрационного клиента.
}  # Завершаем словарь заголовков.

response = requests.get(url, headers=headers, timeout=10)  # Выполняем запрос с пользовательскими заголовками.
response.raise_for_status()  # Проверяем успешность ответа.

print(response.json())  # Показываем разобранный JSON-ответ.
```

Нельзя считать любой заголовок универсальным. Точные названия, обязательность и допустимые значения определяются документацией конкретного API.

# 13. Body — тело запроса

## 13.1. Когда используется тело

Тело запроса обычно используется при:

- создании ресурса;
- полном обновлении;
- частичном обновлении;
- отправке сложного фильтра;
- загрузке файла;
- запуске операции с параметрами.

`GET` обычно передаёт настройки через URL и заголовки, а не через тело. Некоторые системы технически принимают тело `GET`, но его семантика не является общепринятой и может не поддерживаться промежуточными компонентами.

## 13.2. POST с JSON

```python
import requests  # Импортируем библиотеку requests.

url = "https://jsonplaceholder.typicode.com/posts"  # Указываем endpoint для создания тестового объекта.
payload = {  # Создаём словарь с данными нового объекта.
    "title": "Первый API-запрос",  # Передаём заголовок публикации.
    "body": "Демонстрационные данные",  # Передаём текст публикации.
    "userId": 1,  # Передаём идентификатор пользователя.
}  # Завершаем словарь данных.

response = requests.post(url, json=payload, timeout=10)  # Отправляем POST-запрос и поручаем requests преобразовать словарь в JSON.
response.raise_for_status()  # Проверяем успешность HTTP-ответа.

created_post = response.json()  # Преобразуем JSON-ответ в словарь Python.

print("Код ответа:", response.status_code)  # Показываем код, который вернул тестовый сервис.
print("Созданный объект:", created_post)  # Показываем представление созданного тестового объекта.
```

Аргумент `json=payload`:

- сериализует словарь Python в JSON;
- устанавливает подходящий `Content-Type`;
- передаёт JSON в теле запроса.

Не следует одновременно передавать одни и те же данные через `json=` и `data=`.

## 13.3. Form data и JSON — разные форматы

```python
import requests  # Импортируем библиотеку requests.

url = "https://httpbin.org/post"  # Указываем тестовый endpoint, который возвращает сведения о полученном запросе.
form_data = {  # Создаём данные обычной HTML-формы.
    "username": "student",  # Добавляем демонстрационное имя пользователя.
    "course": "api-basics",  # Добавляем демонстрационное значение курса.
}  # Завершаем словарь формы.

response = requests.post(url, data=form_data, timeout=10)  # Передаём данные как form-encoded тело через аргумент data.
response.raise_for_status()  # Проверяем HTTP-статус ответа.

print(response.json()["form"])  # Показываем, какие form-поля получил тестовый сервер.
```

Используйте `json=` только тогда, когда контракт API ожидает JSON. Используйте `data=` только для формата, указанного документацией.

# 14. PUT, PATCH и DELETE на Python

Тестовый сервис может имитировать успешную операцию, не сохраняя изменение постоянно.

## 14.1. PUT

```python
import requests  # Импортируем библиотеку requests.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Указываем адрес существующего тестового ресурса.

response = requests.put(url, json=payload, timeout=10)  # Отправляем PUT-запрос с JSON-телом.
```

```python
import requests  # Импортируем библиотеку requests.
```

# 15. Коды ответа HTTP

## 15.1. Классы кодов

| Диапазон | Смысл |
|---:|---|
| 1xx | информационный ответ |
| 2xx | успешная обработка |
| 3xx | перенаправление или условный результат |
| 4xx | проблема в запросе или правах клиента |
| 5xx | ошибка на стороне сервера или промежуточной инфраструктуры |

## 15.2. Часто встречающиеся коды

| Код | Название | Практический смысл |
|---:|---|---|
| 200 | OK | запрос успешно обработан |
| 201 | Created | ресурс создан |
| 202 | Accepted | запрос принят, обработка может продолжаться асинхронно |
| 204 | No Content | запрос успешен, тела ответа нет |
| 304 | Not Modified | можно использовать кэшированное представление |
| 400 | Bad Request | запрос некорректен |
| 401 | Unauthorized | нет корректной аутентификации |
| 403 | Forbidden | доступ запрещён даже после определения клиента |
| 404 | Not Found | ресурс или endpoint не найден |
| 405 | Method Not Allowed | метод не разрешён для endpoint |
| 409 | Conflict | операция конфликтует с текущим состоянием |
| 415 | Unsupported Media Type | сервер не поддерживает формат тела |
| 422 | Unprocessable Content | структура понятна, но содержимое не прошло обработку или валидацию |
| 429 | Too Many Requests | превышено ограничение частоты запросов |
| 500 | Internal Server Error | внутренняя ошибка сервера |
| 502 | Bad Gateway | шлюз получил некорректный ответ от другой системы |
| 503 | Service Unavailable | сервис временно недоступен |
| 504 | Gateway Timeout | шлюз не дождался ответа зависимой системы |

## 15.3. 401 и 403

Упрощённо:

- `401` — сервер не получил корректные данные для определения и проверки клиента;
- `403` — сервер понял, кто выполняет запрос, но операция этому клиенту не разрешена.

Реальное поведение зависит от политики API. Некоторые системы намеренно возвращают `404`, чтобы не раскрывать существование защищённого ресурса.

## 15.4. 200 не означает, что бизнес-операция завершена

Система может вернуть `200`, но внутри JSON указать бизнес-статус:

```json
{
  "operation_status": "pending"
}
```

Или вернуть `202`, потому что задача только поставлена в очередь.

Поэтому нужно проверять:

- HTTP-код;
- схему ответа;
- бизнес-статус;
- идентификатор операции;
- документацию асинхронной обработки.

# 16. Обработка ошибок в Requests

## 16.1. Основные типы проблем

Запрос может завершиться неуспешно из-за:

- DNS-ошибки;
- отсутствия соединения;
- отказа сервера;
- истечения времени ожидания;
- ошибочного HTTP-статуса;
- некорректного JSON;
- неожидаемой структуры ответа.

## 16.2. Базовый безопасный шаблон

```python
import requests  # Импортируем библиотеку requests и её классы исключений.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Задаём адрес тестового ресурса.

try:  # Начинаем блок обработки ожидаемых сетевых и HTTP-ошибок.
    response = requests.get(url, timeout=10)  # Выполняем GET-запрос с ограничением времени ожидания.
    response.raise_for_status()  # Создаём HTTPError, если сервер вернул статус 4xx или 5xx.
    data = response.json()  # Пытаемся преобразовать тело ответа из JSON в объект Python.
    print("Получены данные:", data)  # Показываем результат успешного запроса.
except requests.exceptions.Timeout:  # Обрабатываем ситуацию, когда сервер не ответил вовремя.
    print("Превышено время ожидания ответа API.")  # Выводим понятное сообщение о тайм-ауте.
except requests.exceptions.ConnectionError:  # Обрабатываем DNS-ошибку, отказ соединения и другие сетевые проблемы.
    print("Не удалось установить сетевое соединение с API.")  # Выводим сообщение о проблеме соединения.
except requests.exceptions.HTTPError as error:  # Обрабатываем ошибочный HTTP-статус.
    print("API вернул ошибочный HTTP-статус:", error)  # Показываем сведения об HTTP-ошибке без сокрытия причины.
except requests.exceptions.JSONDecodeError:  # Обрабатываем ситуацию, когда тело не является корректным JSON.
    print("Ответ получен, но его не удалось разобрать как JSON.")  # Выводим сообщение об ошибке формата ответа.
```

Здесь нет `except Exception`, потому что слишком широкий перехват может скрыть программную ошибку, например опечатку в имени переменной.

## 16.3. Ошибка API тоже может иметь полезное тело

Иногда при статусе `400` сервер возвращает JSON с деталями валидации. Но структура ошибки не универсальна.

Пример возможной схемы:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Поле amount должно быть положительным",
    "field": "amount"
  }
}
```

Перед использованием полей ошибки нужно изучить контракт конкретного API.

## 16.4. Функция для безопасного GET-запроса

```python
from typing import Any  # Импортируем тип Any для обозначения произвольной структуры JSON.

import requests  # Импортируем библиотеку requests.


def get_json(url: str, params: dict[str, Any] | None = None) -> Any:  # Объявляем функцию получения JSON по URL с необязательными параметрами.
    response = requests.get(url, params=params, timeout=10)  # Выполняем GET-запрос с параметрами и тайм-аутом.
    response.raise_for_status()  # Проверяем, что сервер не вернул статус 4xx или 5xx.
    return response.json()  # Возвращаем разобранное JSON-тело вызывающему коду.


url = "https://jsonplaceholder.typicode.com/posts"  # Указываем endpoint коллекции публикаций.
params = {"userId": 1}  # Задаём фильтр по идентификатору пользователя.
posts = get_json(url, params)  # Вызываем созданную функцию и получаем данные.

print("Количество публикаций:", len(posts))  # Выводим число объектов в полученном списке.
```

Эта функция специально остаётся простой. В production-коде дополнительно могут потребоваться логирование, повторные попытки, схема валидации, метрики и трассировка.

# 17. Тайм-ауты

## 17.1. Почему тайм-аут обязателен

Если не указать тайм-аут, программа может слишком долго ожидать сетевой ответ. Это способно остановить обработку данных, очередь задач или пользовательский запрос.

```python
import requests  # Импортируем библиотеку requests.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Указываем адрес тестового ресурса.
response = requests.get(url, timeout=10)  # Ограничиваем ожидание сетевой активности десятью секундами.
response.raise_for_status()  # Проверяем успешность HTTP-ответа.

print(response.json())  # Показываем разобранный JSON-ответ.
```

В `requests` значение `timeout=10` не обязательно означает жёсткий лимит полного времени загрузки. Оно управляет ожиданием сетевой активности в соответствии с поведением библиотеки.

## 17.2. Раздельный connect и read timeout

Более точная настройка:

```python
import requests  # Импортируем библиотеку requests.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Указываем URL тестового API.
timeout = (3.05, 10)  # Задаём отдельно время установления соединения и ожидания данных.

response = requests.get(url, timeout=timeout)  # Выполняем GET-запрос с раздельными тайм-аутами.
response.raise_for_status()  # Проверяем успешность ответа.

print(response.json())  # Показываем полученный JSON.
```

Конкретные значения должны соответствовать назначению сервиса, ожидаемому времени ответа и SLA/SLO интеграции.

# 18. Аутентификация и авторизация

## 18.1. Аутентификация

**Аутентификация** отвечает на вопрос:

> Кто выполняет запрос?

Примеры:

- логин и пароль;
- API-ключ;
- bearer-токен;
- клиентский сертификат;
- подписанный запрос.

## 18.2. Авторизация

**Авторизация** отвечает на вопрос:

> Что этому клиенту разрешено делать?

Например, пользователь может:

- читать свои заказы;
- не иметь доступа к чужим заказам;
- не иметь права удалять данные;
- иметь доступ только к одному проекту.

## 18.3. API key

API-ключ — секретное значение, которое сервис выдаёт клиенту. Способ передачи зависит от API.

Возможные варианты:

```text
X-API-Key: <key>
Authorization: ApiKey <key>
?api_key=<key>
```

Передача секрета в URL нежелательна, потому что URL может попасть в историю, логи и системы мониторинга. Используйте способ из официальной документации.

## 18.4. Bearer token

Распространённый вариант:

```text
Authorization: Bearer <access_token>
```

Bearer-токен предоставляет доступ тому, кто им располагает. Поэтому его нужно защищать как секрет.

## 18.5. Нельзя хранить секрет в исходном коде

Плохой пример:

```python
api_token = "real-secret-token"  # Плохая практика: секрет записан прямо в исходном коде и может попасть в Git.
```

Так делать нельзя.

# 19. Токен через переменную окружения

## 19.1. Временная переменная в PowerShell

```powershell
$env:API_TOKEN = "replace-with-your-token"  # Создаём переменную окружения только для текущего окна PowerShell.
```

## 19.2. Временная переменная в Linux или macOS

```bash
export API_TOKEN="replace-with-your-token"  # Создаём переменную окружения только для текущей shell-сессии.
```

## 19.3. Чтение токена в Python

Следующий пример использует условный URL. Его нельзя запускать без адреса и токена реального разрешённого API.

```python
import os  # Импортируем модуль os для чтения переменных окружения.

import requests  # Импортируем библиотеку requests для выполнения HTTPS-запроса.

api_token = os.getenv("API_TOKEN")  # Получаем токен из переменной окружения API_TOKEN.

if not api_token:  # Проверяем, что переменная окружения существует и не является пустой.
    raise RuntimeError("Переменная окружения API_TOKEN не задана.")  # Останавливаем программу с понятным сообщением без вывода секрета.

url = "https://api.example.com/v1/profile"  # Указываем условный endpoint защищённого API.
headers = {  # Создаём словарь заголовков запроса.
    "Authorization": f"Bearer {api_token}",  # Передаём токен в заголовке Authorization по схеме Bearer.
    "Accept": "application/json",  # Сообщаем, что ожидаем JSON-ответ.
}  # Завершаем словарь заголовков.

response = requests.get(url, headers=headers, timeout=10)  # Выполняем защищённый GET-запрос с тайм-аутом.
response.raise_for_status()  # Проверяем успешность HTTP-ответа.

print(response.json())  # Показываем данные ответа, не выводя значение токена.
```

## 19.4. Правила работы с секретами

- не записывать реальные токены в notebook;
- не добавлять файл с секретами в Git;
- не отправлять токен в чат, письмо или скриншот;
- не печатать полный заголовок `Authorization`;
- использовать минимальные права;
- задавать срок действия;
- отзывать скомпрометированный токен;
- разделять development, test и production;
- применять менеджер секретов в production-среде.

Переменная окружения лучше литерала в коде, но сама по себе не решает все задачи безопасного хранения.

# 20. Проверка Content-Type и структуры ответа

## 20.1. Почему нельзя слепо доверять ответу

Даже при статусе `200` сервер может вернуть:

- HTML-страницу прокси;
- текстовое сообщение;
- JSON другой версии;
- неполный объект;
- список вместо словаря;
- ошибочную структуру.

## 20.2. Простая проверка типа содержимого

```python
import requests  # Импортируем библиотеку requests.

url = "https://jsonplaceholder.typicode.com/posts/1"  # Указываем адрес тестового ресурса.
response = requests.get(url, timeout=10)  # Выполняем GET-запрос с тайм-аутом.
response.raise_for_status()  # Проверяем HTTP-статус ответа.

content_type = response.headers.get("Content-Type", "")  # Получаем Content-Type или пустую строку, если заголовок отсутствует.

if "application/json" not in content_type.lower():  # Проверяем, что сервер заявил JSON-содержимое.
    raise ValueError(f"Ожидался JSON, получен Content-Type: {content_type}")  # Останавливаем обработку при неожиданном формате.

data = response.json()  # Разбираем тело как JSON после проверки типа содержимого.

if not isinstance(data, dict):  # Проверяем, что верхний уровень ответа является объектом JSON.
    raise TypeError("Ожидался JSON-объект.")  # Сообщаем об ошибке структуры.

required_fields = {"id", "title", "body", "userId"}  # Задаём набор обязательных полей демонстрационного ответа.
missing_fields = required_fields - data.keys()  # Определяем, каких обязательных полей нет в ответе.

if missing_fields:  # Проверяем, обнаружены ли отсутствующие поля.
    raise ValueError(f"В ответе отсутствуют поля: {sorted(missing_fields)}")  # Останавливаем обработку и показываем список полей.

print("Ответ прошёл базовую проверку:", data)  # Показываем проверенный объект.
```

Это базовая ручная проверка. Для сложных контрактов применяются JSON Schema, модели данных и специализированные валидаторы.

# 21. Пагинация

## 21.1. Зачем нужна пагинация

API не всегда возвращает все записи одним ответом. Если объектов миллионы, один ответ будет:

- большим;
- медленным;
- дорогим по памяти;
- неудобным для повторной обработки;
- рискованным для сервера.

Поэтому данные делят на страницы.

## 21.2. Page и limit

Пример:

```text
GET /v1/orders?page=3&limit=100
```

## 21.3. Offset и limit

Пример:

```text
GET /v1/orders?offset=200&limit=100
```

## 21.4. Cursor pagination

Пример ответа:

```json
{
  "items": [],
  "next_cursor": "eyJpZCI6NTAwfQ=="
}
```

Следующий запрос:

```text
GET /v1/orders?cursor=eyJpZCI6NTAwfQ==
```

Курсор нельзя самостоятельно разбирать или изменять, если документация не разрешает это.

## 21.5. Универсального стандарта пагинации нет

Разные API используют:

- `page`;
- `offset`;
- `cursor`;
- `next` URL;
- HTTP-заголовки;
- комбинацию подходов.

Клиент должен следовать конкретному контракту.

## 21.6. Пример page-based pagination

Следующий код является шаблоном. Названия `page`, `limit` и структура ответа должны быть адаптированы под документацию API.

```python
from typing import Any  # Импортируем тип Any для произвольных JSON-объектов.

import requests  # Импортируем библиотеку requests.

base_url = "https://api.example.com/v1/items"  # Указываем условный endpoint коллекции.
page = 1  # Начинаем с первой страницы.
page_size = 100  # Запрашиваем до ста объектов на одной странице.
all_items: list[dict[str, Any]] = []  # Создаём список для накопления объектов со всех страниц.

while True:  # Запускаем цикл последовательного получения страниц.
    params = {  # Формируем параметры текущей страницы.
        "page": page,  # Передаём номер текущей страницы.
        "limit": page_size,  # Передаём требуемый размер страницы.
    }  # Завершаем словарь параметров.

    response = requests.get(base_url, params=params, timeout=10)  # Запрашиваем текущую страницу с тайм-аутом.
    response.raise_for_status()  # Проверяем HTTP-статус ответа.

    payload = response.json()  # Преобразуем JSON-ответ в объект Python.
    items = payload.get("items", [])  # Получаем список items или пустой список при отсутствии поля.

    if not isinstance(items, list):  # Проверяем, что поле items действительно содержит список.
        raise TypeError("Поле items должно быть списком.")  # Останавливаем обработку при нарушении контракта.

    all_items.extend(items)  # Добавляем объекты текущей страницы в общий список.

    if len(items) < page_size:  # Считаем последней страницу, содержащую меньше объектов, чем запрошено.
        break  # Завершаем цикл после последней страницы.

    page += 1  # Переходим к следующему номеру страницы.

print("Всего получено объектов:", len(all_items))  # Показываем итоговое количество загруженных объектов.
```

Важно: условие завершения может быть другим. Некоторые API возвращают `has_more`, `total_pages` или `next`.

## 21.7. Пример cursor pagination

```python
from typing import Any  # Импортируем тип Any для произвольных JSON-объектов.

import requests  # Импортируем библиотеку requests.

base_url = "https://api.example.com/v1/items"  # Указываем условный endpoint с cursor pagination.
cursor: str | None = None  # До первого запроса курсор отсутствует.
all_items: list[dict[str, Any]] = []  # Создаём список для накопления всех объектов.

while True:  # Запускаем цикл получения страниц по курсору.
    params = {"limit": 100}  # Задаём размер одной страницы.

    if cursor is not None:  # Проверяем, был ли получен курсор следующей страницы.
        params["cursor"] = cursor  # Добавляем курсор в параметры следующего запроса.

    response = requests.get(base_url, params=params, timeout=10)  # Получаем текущую страницу данных.
    response.raise_for_status()  # Проверяем HTTP-статус ответа.

    payload = response.json()  # Разбираем JSON-ответ.
    items = payload.get("items", [])  # Получаем список объектов текущей страницы.
    cursor = payload.get("next_cursor")  # Получаем курсор следующей страницы.

    if not isinstance(items, list):  # Проверяем тип поля items.
        raise TypeError("Поле items должно быть списком.")  # Останавливаем обработку при нарушении контракта.

    all_items.extend(items)  # Добавляем текущую страницу в общий список.

    if not cursor:  # Проверяем, что сервер больше не вернул курсор продолжения.
        break  # Завершаем цикл после последней страницы.

print("Всего получено объектов:", len(all_items))  # Показываем итоговое количество объектов.
```

# 22. Rate limit и код 429

## 22.1. Что такое rate limit

**Rate limit** — ограничение частоты или объёма запросов.

Примеры:

- 60 запросов в минуту;
- 10 запросов в секунду;
- 100 000 запросов в месяц;
- отдельный лимит для тяжёлого endpoint.

Ограничение защищает сервис от перегрузки и помогает распределять ресурсы.

## 22.2. Что делать при 429

Сервер может вернуть:

```text
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

Это может означать, что повторную попытку следует выполнить позже. Формат `Retry-After` может быть числом секунд или HTTP-датой.

## 22.3. Простой ограниченный retry для GET

Следующий шаблон повторяет только безопасный `GET`. Он не является универсальной retry-библиотекой.

```python
import time  # Импортируем time для ожидания между повторными попытками.

import requests  # Импортируем библиотеку requests.

url = "https://api.example.com/v1/items"  # Указываем условный endpoint для безопасного GET-запроса.
max_attempts = 3  # Ограничиваем общее число попыток, чтобы избежать бесконечного цикла.

for attempt in range(1, max_attempts + 1):  # Последовательно выполняем не более трёх попыток.
    response = requests.get(url, timeout=10)  # Отправляем GET-запрос с тайм-аутом.

    if response.status_code == 429:  # Проверяем, не превышен ли rate limit.
        retry_after = response.headers.get("Retry-After", "1")  # Получаем рекомендуемое время ожидания или используем одну секунду.

        if retry_after.isdigit():  # Проверяем, что Retry-After содержит целое число секунд.
            wait_seconds = min(int(retry_after), 60)  # Ограничиваем ожидание шестьюдесятью секундами в демонстрационном скрипте.
        else:  # Обрабатываем другой формат Retry-After без разбора HTTP-даты.
            wait_seconds = 1  # Используем короткое безопасное ожидание для примера.

        print(f"Rate limit. Повтор через {wait_seconds} сек.")  # Сообщаем причину и время ожидания.
        time.sleep(wait_seconds)  # Приостанавливаем программу перед следующей попыткой.
        continue  # Переходим к следующей итерации цикла.

    response.raise_for_status()  # Проверяем остальные ошибочные HTTP-статусы.
    data = response.json()  # Разбираем успешный JSON-ответ.
    print(data)  # Показываем полученные данные.
    break  # Завершаем цикл после успешного запроса.
else:  # Выполняем этот блок, если цикл завершился без break.
    raise RuntimeError("Не удалось получить данные после повторных попыток.")  # Сообщаем о контролируемом исчерпании попыток.
```

Нельзя автоматически повторять любой `POST`: повтор может создать дубликат операции. Retry policy должна учитывать метод, идемпотентность и контракт сервера.

# 23. Идемпотентность

## 23.1. Простое определение

Операция идемпотентна, если повтор одинакового запроса не создаёт дополнительного изменения состояния по сравнению с одним запросом.

Пример:

```text
PUT /v1/users/42
```

с одинаковым полным телом ожидаемо приводит пользователя к одному и тому же состоянию.

## 23.2. Почему POST опасно повторять автоматически

```text
POST /v1/payments
```

Если первый запрос был обработан, но клиент не получил ответ из-за сетевого разрыва, повтор может создать второй платёж.

## 23.3. Idempotency-Key

Некоторые API поддерживают специальный ключ идемпотентности:

```text
Idempotency-Key: 3f19c1f2-...
```

Сервер может связать повторные запросы с одной операцией.

Это не универсальный HTTP-заголовок для всех API. Его имя, срок хранения и поведение определяются документацией сервиса.

Пример условного запроса:

```python
import uuid  # Импортируем модуль uuid для создания уникального идентификатора операции.

import requests  # Импортируем библиотеку requests.

url = "https://api.example.com/v1/payments"  # Указываем условный endpoint создания платежа.
idempotency_key = str(uuid.uuid4())  # Создаём уникальный ключ для одной бизнес-операции.
headers = {  # Формируем заголовки условного API.
    "Idempotency-Key": idempotency_key,  # Передаём ключ идемпотентности, если API официально его поддерживает.
    "Content-Type": "application/json",  # Указываем формат тела запроса.
}  # Завершаем словарь заголовков.
payload = {  # Формируем демонстрационные данные платежа.
    "order_id": 501,  # Указываем идентификатор заказа.
    "amount": 3490.0,  # Указываем сумму операции.
}  # Завершаем словарь данных.

response = requests.post(url, headers=headers, json=payload, timeout=10)  # Отправляем условный POST-запрос с ключом идемпотентности.
response.raise_for_status()  # Проверяем успешность HTTP-ответа.

print(response.json())  # Показываем ответ без вывода секретов.
```

Не запускайте этот шаблон против реальной платёжной системы без согласованного контракта и тестовой среды.

# 24. Повторные попытки и backoff

Повторная попытка уместна не для каждой ошибки.

Часто можно рассматривать повтор для:

- временной сетевой ошибки;
- `429`;
- `502`;
- `503`;
- `504`.

Обычно не следует автоматически повторять без изменения запроса:

- `400`;
- `401`;
- `403`;
- `404`;
- ошибку валидации;
- неидемпотентную операцию без защиты от дублей.

**Backoff** — постепенное увеличение паузы между попытками.

Пример:

```text
1-я пауза: 1 секунда
2-я пауза: 2 секунды
3-я пауза: 4 секунды
```

В распределённых системах часто добавляют случайную составляющую — jitter, чтобы много клиентов не повторили запрос одновременно.

Для начинающего уровня важно запомнить:

> Повтор — это часть контракта надёжности, а не универсальное средство исправить любую ошибку.

# 25. Session в Requests

Если программа выполняет много запросов к одному серверу, можно использовать `requests.Session`.

Session позволяет:

- повторно использовать соединения;
- сохранять общие заголовки;
- сохранять cookies;
- применять общие настройки к нескольким запросам.

```python
import requests  # Импортируем библиотеку requests.

base_url = "https://jsonplaceholder.typicode.com"  # Сохраняем базовый адрес тестового API.

with requests.Session() as session:  # Создаём Session и гарантируем закрытие ресурсов после блока.
    session.headers.update({  # Добавляем общие заголовки для всех запросов Session.
        "Accept": "application/json",  # Сообщаем, что ожидаем JSON-ответы.
        "User-Agent": "beginner-api-client/1.0",  # Указываем имя демонстрационного клиента.
    })  # Завершаем обновление заголовков Session.

    first_response = session.get(f"{base_url}/posts/1", timeout=10)  # Получаем первую публикацию через Session.
    first_response.raise_for_status()  # Проверяем успешность первого ответа.

    second_response = session.get(f"{base_url}/posts/2", timeout=10)  # Получаем вторую публикацию через ту же Session.
    second_response.raise_for_status()  # Проверяем успешность второго ответа.

    print(first_response.json())  # Показываем первую публикацию.
    print(second_response.json())  # Показываем вторую публикацию.
```

Session не отменяет необходимость тайм-аутов, обработки ошибок и проверки данных.

# 27. Вложенный JSON и json_normalize

API может возвращать вложенные объекты:

```json
{
  "id": 501,
  "customer": {
    "id": 17,
    "name": "Анна"
  },
  "items": [
    {
      "product_id": 7,
      "quantity": 2
    }
  ]
}
```

Для преобразования вложенных объектов в таблицу можно использовать `pandas.json_normalize`.

```python
import pandas as pd  # Импортируем pandas для нормализации JSON и создания таблицы.

data = [  # Создаём демонстрационный список заказов.
    {  # Начинаем описание первого заказа.
        "id": 501,  # Добавляем идентификатор заказа.
        "status": "paid",  # Добавляем статус заказа.
        "customer": {  # Добавляем вложенный объект клиента.
            "id": 17,  # Добавляем идентификатор клиента.
            "name": "Анна",  # Добавляем имя клиента.
        },  # Завершаем вложенный объект клиента.
    },  # Завершаем первый заказ.
]  # Завершаем список заказов.

df = pd.json_normalize(data, sep="_")  # Преобразуем вложенные поля в плоские столбцы с разделителем подчёркивания.

print(df)  # Показываем нормализованную таблицу.
```

Результат будет содержать поля вроде:

```text
id
status
customer_id
customer_name
```

Массивы внутри JSON требуют отдельного решения. Нельзя бездумно разворачивать массивы: одна строка заказа может превратиться в несколько строк позиций, и grain таблицы изменится.

# 28. Grain ответа и риск дублирования

**Grain** — смысл одной строки или одного объекта.

Примеры:

- одна строка = один заказ;
- одна строка = одна позиция заказа;
- одна строка = один клиент за день;
- одна строка = одно событие.

Если API возвращает заказ и массив позиций, после разворачивания:

```text
заказ 501, товар 7
заказ 501, товар 8
заказ 501, товар 9
```

Заказ повторяется три раза. Если затем просуммировать поле `order_amount`, выручка будет завышена.

Перед преобразованием ответа нужно определить:

- единицу объекта API;
- уникальный ключ;
- вложенные массивы;
- связи one-to-many;
- нужный уровень итоговой таблицы;
- правила агрегации.

Это особенно важно для аналитики.

# 29. Загрузка и скачивание файлов

## 29.1. Скачивание файла потоками

```python
from pathlib import Path  # Импортируем Path для безопасной работы с путями файлов.

import requests  # Импортируем requests для загрузки файла по HTTPS.

url = "https://example.com/files/report.csv"  # Указываем условный адрес разрешённого файла.
output_path = Path("report.csv")  # Создаём объект пути для локального файла.

with requests.get(url, stream=True, timeout=30) as response:  # Открываем потоковый GET-запрос и гарантируем закрытие соединения.
    response.raise_for_status()  # Проверяем успешность HTTP-ответа перед записью файла.

    with output_path.open("wb") as file:  # Открываем локальный файл в бинарном режиме записи.
        for chunk in response.iter_content(chunk_size=8192):  # Последовательно получаем части файла по 8192 байта.
            if chunk:  # Пропускаем пустые служебные части потока.
                file.write(chunk)  # Записываем текущую часть в локальный файл.

print("Файл сохранён:", output_path)  # Показываем путь сохранённого файла.
```

Перед загрузкой крупного файла нужно учитывать:

- допустимый размер;
- свободное место;
- тип содержимого;
- контрольную сумму;
- правила именования;
- права доступа;
- отсутствие перезаписи важного файла.

## 29.2. Отправка файла multipart/form-data

```python
from pathlib import Path  # Импортируем Path для работы с локальным путём.

import requests  # Импортируем requests для отправки файла.

url = "https://api.example.com/v1/uploads"  # Указываем условный endpoint загрузки файла.
file_path = Path("report.csv")  # Создаём объект пути к отправляемому файлу.

if not file_path.is_file():  # Проверяем существование обычного файла по указанному пути.
    raise FileNotFoundError(f"Файл не найден: {file_path}")  # Останавливаем выполнение с понятным сообщением.

with file_path.open("rb") as file:  # Открываем файл в бинарном режиме чтения и гарантируем его закрытие.
    files = {  # Создаём структуру multipart-поля.
        "file": (file_path.name, file, "text/csv"),  # Передаём имя файла, файловый объект и заявленный media type.
    }  # Завершаем словарь файлов.

    response = requests.post(url, files=files, timeout=30)  # Отправляем файл на условный endpoint с тайм-аутом.
    response.raise_for_status()  # Проверяем успешность HTTP-ответа.

print(response.json())  # Показываем JSON-ответ сервера после успешной загрузки.
```

Поле `file`, допустимые типы, максимальный размер и схема ответа должны быть взяты из документации API.

# 30. Версионирование API

API меняется. Добавляются поля, меняются правила и удаляются старые возможности.

Распространённые варианты версионирования:

### Версия в URL

```text
/api/v1/orders
/api/v2/orders
```

### Версия в заголовке

```text
Accept: application/vnd.example.v2+json
```

### Версия через параметр

```text
/api/orders?version=2
```

Версия в URL является распространённым подходом, но не обязательным требованием REST.

Клиенту нужно знать:

- текущую версию;
- дату прекращения поддержки;
- изменения схемы;
- правила совместимости;
- план миграции;
- тесты регрессии.

Нельзя считать добавление нового поля полностью безопасным, если клиент жёстко проверяет точный набор полей или зависит от их порядка.

# 31. API contract

## 31.1. Что такое контракт

**API contract** — согласованное описание взаимодействия клиента и сервера.

Контракт должен отвечать на вопросы:

- какой метод использовать;
- какой endpoint вызвать;
- какая авторизация нужна;
- какие path и query parameters доступны;
- какие заголовки обязательны;
- как выглядит request body;
- как выглядит response body;
- какие поля обязательны;
- какие проверки выполняются;
- какие коды ошибок возможны;
- как устроена пагинация;
- действует ли rate limit;
- как обеспечивается идемпотентность;
- какая версия используется.

## 31.2. Пример краткой спецификации операции

```markdown
## Получить заказ

- Method: GET
- Endpoint: /api/v1/orders/{order_id}
- Назначение: получить представление одного заказа
- Авторизация: Bearer token
- Path parameter: order_id — положительное целое число
- Успешный ответ: 200 application/json
- Ошибки: определяются официальным контрактом
- Идемпотентность: да
- Тайм-аут клиента: определяется требованиями интеграции
```

Нельзя придумывать реальные error codes, поля и лимиты, если они должны быть подтверждены владельцем API.

## 31.3. OpenAPI и Swagger

**OpenAPI Specification** — машиночитаемый формат описания HTTP API.

Он может описывать:

- endpoints;
- методы;
- параметры;
- схемы запросов;
- схемы ответов;
- аутентификацию;
- коды ответа.

**Swagger** — название набора инструментов, связанных с проектированием и просмотром API-документации. В разговорной речи Swagger часто называют страницу документации, но спецификация называется OpenAPI.

- поведение при ошибке;

- возможность отмены;
- повторяемость операции.

# 33. Webhook

Обычный API-запрос инициирует клиент. Webhook позволяет одной системе вызвать endpoint другой системы при наступлении события.

Пример:

```text
платёжная система
       |
       | POST /webhooks/payment-completed
       v
интернет-магазин
```

Webhook должен учитывать:

- проверку подписи;
- повторную доставку;
- дубликаты;
- порядок событий;
- идемпотентную обработку;
- быстрый ответ;
- журналирование;
- защиту endpoint;
- replay attack;
- dead-letter или ручное восстановление.

Получатель не должен считать, что событие придёт только один раз.

# 33.1. CORS: почему запрос работает в Python, но может не работать в браузере

**CORS — Cross-Origin Resource Sharing** — механизм браузера, который контролирует запросы веб-страницы к другому origin. Origin определяется сочетанием схемы, хоста и порта.

Важное различие:

- `requests` запускается как Python-клиент и не применяет браузерную политику CORS;
- JavaScript в браузере подчиняется CORS и может быть заблокирован браузером, если сервер не вернул необходимые заголовки;
- исправление CORS обычно выполняется на сервере или API gateway, а не отключением защиты у пользователя.

CORS не является способом аутентификации и не защищает API от прямых запросов других программ. API всё равно должно проверять токены, права, входные данные и ограничения.

# 34. Наблюдаемость интеграции

Рабочая интеграция должна позволять понять:

- был ли отправлен запрос;
- какой endpoint вызван;
- какой статус получен;
- сколько времени занял ответ;
- сколько записей получено;
- была ли повторная попытка;
- где возникла ошибка;
- какой request ID связан с операцией.

При этом нельзя записывать в логи:

- полный токен;
- пароль;
- персональные данные без необходимости;
- полный документ с конфиденциальными полями;
- банковские реквизиты;
- закрытые URL с секретными параметрами.

Пример безопасного минимального сообщения:

```text
endpoint=/v1/orders status=200 duration_ms=184 records=100 request_id=abc-123
```

Логи должны помогать диагностике, но не становиться источником утечки.

# 36. Типовые ошибки начинающих

## Ошибка 1. Считать API сайтом

API может не иметь визуального интерфейса и возвращать JSON вместо страницы.

## Ошибка 2. Считать REST протоколом

REST — архитектурный стиль; HTTP — протокол прикладного уровня.

## Ошибка 3. Считать JSON обязательным для REST

JSON распространён, но REST не ограничен только JSON.

## Ошибка 4. Не устанавливать timeout

Запрос может зависнуть на неопределённое время ожидания сетевой активности.

## Ошибка 5. Вызывать `response.json()` без проверки статуса

Ошибка API тоже может быть JSON. Сначала нужно оценить статус.

## Ошибка 6. Хранить токен в коде

Секрет может попасть в Git, историю notebook или сообщение об ошибке.

## Ошибка 7. Печатать Authorization в лог

Так можно раскрыть токен.

## Ошибка 8. Повторять POST после любой ошибки

Повтор может создать дубликат заказа или платежа.

## Ошибка 9. Получить только первую страницу

Аналитик может ошибочно считать неполную выборку полным датасетом.

## Ошибка 10. Не проверять схему ответа

Изменение поля может сломать обработку или привести к тихой ошибке.

## Ошибка 11. Считать 200 доказательством бизнес-успеха

Операция может быть поставлена в очередь, иметь статус `pending` или содержать бизнес-ошибку.

## Ошибка 12. Использовать production для эксперимента

`POST`, `PATCH` и `DELETE` могут изменить реальные данные.

## Ошибка 13. Отключать проверку TLS

Не используйте `verify=False` как универсальное решение проблем сертификата. Это отключает важную проверку защищённого соединения.

## Ошибка 14. Игнорировать grain

Разворачивание вложенных массивов может продублировать сумму или количество объектов.

# 38. Мини-проект: загрузка данных API в CSV

Этот пример объединяет базовые элементы:

- GET;
- query parameters;
- timeout;
- проверку статуса;
- проверку JSON;
- создание DataFrame;
- проверку схемы;
- сохранение CSV.

```python
from pathlib import Path  # Импортируем Path для работы с выходным файлом.

import pandas as pd  # Импортируем pandas для создания и проверки таблицы.
import requests  # Импортируем requests для выполнения HTTP-запроса.

url = "https://jsonplaceholder.typicode.com/posts"  # Указываем endpoint коллекции тестовых публикаций.
params = {  # Создаём параметры фильтрации запроса.
    "userId": 1,  # Запрашиваем только публикации пользователя с идентификатором 1.
}  # Завершаем словарь параметров.
output_path = Path("posts_user_1.csv")  # Задаём относительный путь выходного CSV-файла.

try:  # Начинаем обработку ожидаемых сетевых и HTTP-ошибок.
    response = requests.get(url, params=params, timeout=10)  # Выполняем GET-запрос с параметрами и тайм-аутом.
    response.raise_for_status()  # Проверяем, что сервер не вернул статус 4xx или 5xx.
    records = response.json()  # Пытаемся преобразовать JSON-массив в объект Python.
except requests.exceptions.Timeout:  # Обрабатываем превышение времени ожидания.
    print("API не ответил за установленное время.")  # Выводим понятное сообщение о тайм-ауте.
except requests.exceptions.ConnectionError:  # Обрабатываем проблему DNS или сетевого соединения.
    print("Не удалось подключиться к API.")  # Выводим сообщение о сетевой проблеме.
except requests.exceptions.HTTPError as error:  # Обрабатываем ошибочный HTTP-статус.
    print("API вернул HTTP-ошибку:", error)  # Показываем сведения об ошибке.
except requests.exceptions.JSONDecodeError:  # Обрабатываем некорректный JSON.
    print("Ответ API не является корректным JSON.")  # Сообщаем о проблеме формата.
else:  # Переходим к обработке данных только после успешного запроса.
    if not isinstance(records, list):  # Проверяем, что верхний уровень JSON является списком.
        raise TypeError("Ожидался список записей.")  # Останавливаем выполнение при неожиданной структуре.

    df = pd.DataFrame(records)  # Преобразуем список словарей в DataFrame.
    required_columns = {"userId", "id", "title", "body"}  # Определяем обязательные столбцы тестового контракта.
    missing_columns = required_columns - set(df.columns)  # Находим отсутствующие обязательные столбцы.

    if missing_columns:  # Проверяем наличие ошибки схемы.
        raise ValueError(f"Отсутствуют столбцы: {sorted(missing_columns)}")  # Останавливаем обработку при нарушении схемы.

    duplicate_ids = df["id"].duplicated().sum()  # Считаем повторные идентификаторы публикаций.

    print("Получено строк:", len(df))  # Показываем количество полученных объектов.
    print("Повторных id:", duplicate_ids)  # Показываем количество дубликатов по ключу.
    print("Пропуски по столбцам:")  # Выводим заголовок отчёта по пропускам.
    print(df.isna().sum())  # Показываем количество пропусков в каждом столбце.

    df.to_csv(output_path, index=False, encoding="utf-8")  # Сохраняем проверенные данные в CSV без индекса pandas.
    print("Файл сохранён:", output_path)  # Показываем путь итогового файла.
```

Статус этого примера:

- синтаксис можно проверить локально;
- фактический результат зависит от доступности внешнего тестового API;
- тестовый сервис не является production-источником данных;
- перед реальным использованием нужно адаптировать endpoint, контракт, авторизацию и пагинацию.

# 43. Итог

API позволяет программам взаимодействовать через согласованный контракт. Web API обычно использует HTTP или HTTPS, а REST задаёт архитектурные принципы работы с ресурсами и единообразным интерфейсом.

Базовая цепочка выглядит так:

```text
цель интеграции
→ официальный контракт
→ метод и endpoint
→ параметры, headers и body
→ HTTPS-запрос
→ HTTP-статус
→ проверка JSON и схемы
→ пагинация
→ преобразование данных
→ контроль качества
→ сохранение результата
```

Надёжная работа с API не заканчивается строкой `requests.get()`. Нужно учитывать тайм-ауты, ошибки, авторизацию, rate limits, идемпотентность, пагинацию, безопасность секретов, структуру ответа и единицу данных.

Главный практический принцип:

> Сначала понять контракт и ожидаемый результат, затем писать запрос, после этого проверять не только сетевой ответ, но и качество полученных данных.
