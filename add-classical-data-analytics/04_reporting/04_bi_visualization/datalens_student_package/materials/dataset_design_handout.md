# Проектирование датасетов в BI

## Раздаточный материал

## 1. Датасет начинается не с таблицы, а с вопроса

Перед добавлением полей сформулируйте:

1. Кто будет использовать результат?
2. Какое решение должен принять пользователь?
3. Какие вопросы должен отвечать дашборд?
4. Какая детализация нужна?
5. Какие показатели должны быть согласованы?

Пример:

```text
Пользователь: руководитель службы поддержки.
Решение: перераспределить нагрузку и найти проблемные категории.
Вопросы: сколько обращений, как меняется поток, где дольше решают, где чаще нарушают SLA.
```

## 2. Гранулярность: что означает одна строка

Гранулярность — точное определение единицы наблюдения.

Примеры:

| Датасет | Одна строка |
|---|---|
| обращения | одно обращение |
| дневная динамика | один календарный день |
| клиенты | один клиент |
| сводка гипотез | одна группа внутри гипотезы |
| ошибки прогнозов | одна модель и одна метрика |

### Почему это важно

Если соединить таблицы разной гранулярности без правила, показатели могут размножиться. Например, если к каждому обращению присоединить несколько строк статистической сводки, количество обращений станет завышенным.

### Контрольный вопрос

```text
Можно ли одним предложением объяснить, что означает строка итогового датасета?
```

Если нет — модель ещё не спроектирована.

## 3. Таблица фактов и измерения

### Таблица фактов

Обычно содержит:

- повторяющиеся события;
- даты;
- числовые показатели;
- внешние ключи.

В кейсе `support_tickets` содержит обращения, время ответа, время решения, оценку и ссылки на клиента и регион.

### Справочник или измерение

Обычно содержит:

- одну строку на объект;
- уникальный ключ;
- описательные атрибуты.

`customers` описывает клиента, `regions` — регион.

## 4. Измерения и показатели в DataLens

### Измерение

Поле, по которому данные разбиваются на группы или фильтруются:

- дата;
- канал;
- регион;
- категория;
- приоритет;
- сегмент.

### Показатель

Числовое выражение, которое агрегируется:

- количество обращений;
- средняя оценка;
- среднее время решения;
- доля SLA.

### Идентификатор не является обычным показателем

`ticket_id` нельзя суммировать и усреднять. Для числа обращений используется:

```text
COUNTD([ticket_id])
```

## 5. Тип данных, роль и агрегация — разные свойства

Пример `sla_breached`:

- технический тип: число;
- значения: 0 и 1;
- роль: признак нарушения;
- агрегация `AVG`: доля нарушений;
- агрегация `SUM`: число нарушений.

Пример `ticket_id`:

- технический тип: строка;
- роль: идентификатор;
- корректная агрегация для количества: `COUNTD`.

## 6. Где создавать вычисляемое поле

### На уровне датасета

Используйте, если поле:

- нужно в нескольких чартах;
- должно иметь единое определение;
- используется селектором;
- входит в официальную методологию KPI.

### На уровне чарта

Используйте для локального эксперимента, который не нужен другим объектам.

Главное правило:

```text
Общий бизнес-показатель создаётся один раз в датасете, а не заново в каждом чарте.
```

## 7. Слой подготовки данных и слой BI

Не каждую проблему нужно решать формулой в DataLens.

### На уровне источника или витрины лучше исправлять

- дубли;
- разные кодировки;
- несогласованные ключи;
- сложную очистку текста;
- бизнес-правила, которые должны быть едины для разных систем;
- тяжёлые предварительные расчёты.

### В датасете DataLens удобно фиксировать

- роли и типы;
- простые вычисляемые поля;
- правила агрегации;
- понятные названия;
- фильтры и параметры;
- связи таблиц одного источника.

## 8. Разные гранулярности — разные датасеты

В учебном решении используются отдельные датасеты:

```text
Обращения: одно обращение на строку.
Динамика: один день на строку.
Гипотезы: одна группа гипотезы на строку.
Метрики прогнозов: одна модель и одна метрика на строку.
```

Их не нужно механически объединять. На дашборде они могут сосуществовать как отдельные чарты. При необходимости селекторы между разными датасетами связываются осознанно через совместимые поля и алиасы.

## 9. Карточка проектирования датасета

Перед созданием заполните:

```text
Название:
Пользователь:
Решение пользователя:
Основные вопросы:
Гранулярность:
Таблица фактов:
Справочники:
Первичный ключ факта:
Внешние ключи:
Дата анализа:
Измерения:
Показатели:
Вычисляемые поля:
Обязательные фильтры:
Контрольные значения:
Владелец определения KPI:
Частота обновления:
Ограничения:
```

## 10. QA датасета

### Структура

- [ ] гранулярность определена;
- [ ] ключ строки понятен;
- [ ] нет случайного смешения уровней детализации;
- [ ] поля названы однозначно;
- [ ] лишние технические поля скрыты.

### Типы и роли

- [ ] даты имеют тип «Дата» или «Дата и время»;
- [ ] числовые показатели распознаны как числа;
- [ ] идентификаторы не агрегируются как суммы;
- [ ] категории используются как измерения;
- [ ] единицы измерения зафиксированы.

### Агрегации

- [ ] количество событий считается корректно;
- [ ] доли имеют понятный числитель и знаменатель;
- [ ] среднее не используется там, где нужна сумма или медиана;
- [ ] пропуски не превращены в нули без бизнес-основания;
- [ ] KPI совпадают с контрольными расчётами.

### Производственная готовность

- [ ] понятен источник данных;
- [ ] понятна частота обновления;
- [ ] понятно, что произойдёт при изменении схемы;
- [ ] определены права доступа;
- [ ] нет публичной публикации чувствительных данных.

## 11. Антипаттерны

### «Один огромный датасет на всё»

Результат: смешение гранулярностей, дубли, сложные зависимости и трудно проверяемые KPI.

### «Показатель в каждом чарте считается по-разному»

Результат: разные цифры с одинаковым названием.

### «Все числовые поля — показатели»

Результат: суммирование идентификаторов и кодов.

### «Очистим данные прямо формулами в десяти чартах»

Результат: логика расходится и плохо сопровождается.

### «Если чарт выглядит правдоподобно, модель верна»

Результат: незаметные потери или размножение строк.

## 12. Мини-пример для кейса поддержки

```text
Название: Support Service — BI Mart
Пользователь: руководитель поддержки
Гранулярность: одно уникальное обращение
Ключ: ticket_id
Дата: created_date
Измерения: канал, категория, приоритет, регион, сегмент, SLA
Показатели: COUNTD обращений, средняя оценка, среднее время решения, доля SLA
Контроль: 1500 обращений, 4,13 оценки, 20,39 ч, 34,53% SLA
```
