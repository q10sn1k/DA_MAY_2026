# Связи таблиц и JOIN в DataLens

## Раздаточный материал

## 1. Зачем нужны связи

Данные часто разделены на несколько таблиц:

- события или операции;
- клиенты;
- продукты;
- регионы;
- сотрудники;
- классификаторы.

Связь позволяет дополнить факт атрибутами справочника. В кейсе обращения получают сегмент клиента и название региона.

## 2. Ключи

### Первичный ключ

Поле или набор полей, который однозначно определяет строку справочника.

Примеры:

- `customers.customer_id`;
- `regions.region_id`.

### Внешний ключ

Поле в таблице фактов, которое ссылается на ключ справочника.

Примеры:

- `support_tickets.customer_id`;
- `support_tickets.region_id`.

## 3. Кардинальность

### Один ко многим

Один клиент может иметь много обращений:

```text
customers 1 ─── N support_tickets
```

Это нормальная связь факта со справочником.

### Один к одному

Каждой строке одной таблицы соответствует максимум одна строка другой. Используется реже и требует явного смысла.

### Многие ко многим

Одна строка слева соответствует нескольким справа и наоборот. Прямой JOIN часто размножает строки. Обычно нужна таблица-мост или предварительная агрегация.

## 4. Типы JOIN

### LEFT JOIN

Сохраняет все строки левой таблицы и добавляет совпавшие атрибуты справа.

Используйте, когда левая таблица содержит факты, которые нельзя терять.

В кейсе:

```text
support_tickets LEFT JOIN regions
```

Обращение с неизвестным регионом останется, а название региона будет пустым.

### INNER JOIN

Оставляет только строки, которые имеют совпадение с обеих сторон.

Риск: факт с плохим или отсутствующим ключом исчезнет и KPI может уменьшиться незаметно.

### RIGHT JOIN

Сохраняет все строки правой таблицы. Обычно модель легче читать, если поменять таблицы местами и использовать LEFT JOIN.

### FULL JOIN

Сохраняет строки обеих сторон. Полезен для сверки двух наборов, но редко является основной связью фактов со справочником.

## 5. Как настроить связь в DataLens

1. Создайте датасет.
2. На вкладке **Источники** добавьте таблицы из одного подключения.
3. Нажмите линию между таблицами.
4. Выберите `inner`, `left`, `right` или `full`.
5. Выберите поля связи.
6. Убедитесь, что типы полей совпадают.
7. При необходимости добавьте вторую пару ключей.
8. Решите, нужна ли опция **Оптимизировать связь**.
9. Примените и сохраните.

DataLens может автоматически создать связь по первому совпадению имени и типа полей. Эту связь всегда нужно проверить вручную.

## 6. Требование одинакового типа

Связать можно поля одного типа.

Проблемный пример:

```text
fact.customer_id = строка "42"
dim.customer_id  = число 42
```

Варианты исправления:

- привести типы в источнике;
- использовать SQL-преобразование для источника-БД;
- подготовить корректную витрину.

Не пытайтесь скрыть проблему визуальной настройкой чарта.

## 7. Оптимизация связи

Когда опция включена, DataLens может не выполнять JOIN, если чарт использует поля только одной таблицы. Это уменьшает объём запроса, но иногда приводит к результату, который отличается от интуитивно ожидаемого.

### Когда оставить включённой

- модель проверена;
- важна производительность;
- пользователь понимает, какие таблицы реально участвуют в запросе.

### Когда временно отключить

- учебная демонстрация JOIN;
- нужно гарантировать применение связи;
- проверяется влияние отсутствующих ключей;
- результат без JOIN может запутать пользователя.

После обучения решение должно приниматься осознанно, а не автоматически.

## 8. Главный риск: размножение строк

Пример:

```text
Факт: 1 строка обращения T1.
Справочник: две строки с customer_id = C1.
После JOIN: обращение T1 появится дважды.
```

Последствия:

- сумма удвоится;
- среднее может измениться;
- количество строк станет больше;
- часть KPI будет выглядеть правдоподобно, но окажется неверной.

### Защита

Перед JOIN проверьте уникальность ключа справочника. После JOIN сравните число строк и уникальных ключей факта.

## 9. Второй риск: потеря строк

При `INNER JOIN` факт без совпадения удаляется.

В кейсе 28 уникальных обращений не имеют корректно сопоставленного региона. `LEFT JOIN` сохраняет их, `INNER JOIN` исключит.

## 10. Третий риск: дубликаты исходного факта

JOIN может быть корректным, но таблица фактов уже содержит повторные идентификаторы.

В исходном журнале:

- 1510 строк;
- 1500 уникальных `ticket_id`.

Поэтому нужно различать:

```text
COUNT([ticket_id])  = число непустых записей
COUNTD([ticket_id]) = число уникальных обращений
```

`COUNTD` защищает KPI, но не заменяет очистку данных.

## 11. Чек-лист до JOIN

- [ ] определена левая таблица;
- [ ] сформулировано, какие строки должны сохраниться;
- [ ] известна кардинальность;
- [ ] ключ справочника уникален;
- [ ] ключи имеют одинаковый тип;
- [ ] нет лишних пробелов и различий регистра;
- [ ] понятна политика отсутствующих ключей;
- [ ] выбран тип JOIN.

## 12. Чек-лист после JOIN

- [ ] число строк не увеличилось неожиданно;
- [ ] уникальные ключи факта не потерялись;
- [ ] посчитано число несовпавших ключей;
- [ ] проверены пустые атрибуты справочника;
- [ ] дубли полей связи удалены или скрыты;
- [ ] KPI сверены с контрольными значениями;
- [ ] проверено поведение с включённой и отключённой оптимизацией, если это важно.

## 13. QA-таблица для кейса

| Проверка | Ожидается |
|---|---:|
| строки исходного факта | 1510 |
| уникальные обращения | 1500 |
| строки после присоединения справочников | 1510 |

| уникальные обращения без региона | 28 |

## 14. Как выбрать JOIN по вопросу

| Вопрос | Обычно подходит |
|---|---|
| сохранить все операции и обогатить справочником | LEFT JOIN |
| анализировать только подтверждённые совпадения | INNER JOIN |
| найти несовпадения двух реестров | FULL JOIN и фильтр пустых ключей |
| сохранить все строки правой таблицы | RIGHT JOIN или переставить таблицы и использовать LEFT |

## 15. Формула объяснения связи

Перед сохранением модели аналитик должен завершить предложение:

```text
Мы соединяем [левую таблицу] с [правой таблицей]
по полям [ключи]
типом [JOIN],
потому что хотим сохранить [какие строки],
а качество проверим через [контрольные показатели].
```

Пример:

```text
Мы соединяем обращения с регионами по region_id типом LEFT JOIN,
потому что хотим сохранить все обращения,
а качество проверим числом строк, COUNTD(ticket_id)
и количеством пустых region_name.
```
