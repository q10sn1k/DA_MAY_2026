# Правила качества и очистки

## 1. Общий порядок

1. Проверить наличие файлов и кодировку.
2. Прочитать таблицы без автоматического удаления строк.
3. Зафиксировать исходное число строк и уникальных ключей.
4. Преобразовать даты с `errors="coerce"`.
5. Нормализовать текстовые категории через `str.strip().str.lower()`.
6. Удалять или исправлять данные только по явно сформулированному правилу.
7. После каждого шага повторно считать строки и нарушения.
8. Сохранять отдельный отчёт качества.

## 2. `tickets.csv`

### Дедупликация

- ключ: `ticket_id`;
- перед дедупликацией сортировать по `source_updated_at`;
- сохранять последнюю версию записи;
- контроль: 24 240 строк превращаются в 24 000 уникальных обращений.

### Фатальные нарушения

Исключаются:

- 24 строки с нераспознаваемым `created_at_utc`;
- 36 строк, где `closed_at_utc < created_at_utc`;
- 18 строк с `team_id`, отсутствующим в справочнике команд.

После дедупликации и исключений должно остаться 23 922 обращения.

### Исправляемые нарушения

- 144 нестандартизованных значения `channel`;
- 90 нестандартизованных значений `priority`;
- 96 пропусков `region_id`, восстанавливаемых через справочник команды;
- 48 отрицательных значений `first_response_min`, заменяемых на пропуск;
- 120 значений `csat` вне диапазона 1–5, заменяемых на пропуск.

### Проверки бизнес-правил

- `resolution_min >= 0`;
- `sla_target_min > 0`;
- `sla_breached` принимает 0, 1 или null;
- у нерешённых обращений `resolved_at_utc`, `resolution_min` и `sla_breached` должны быть пустыми;
- `created_hour_local` находится в диапазоне 0–23;
- `created_weekday` находится в диапазоне 0–6.

## 3. `ticket_events.csv`

Контролируемые нарушения:

- 600 полных дублей по `event_id`;
- 80 событий с неизвестным `ticket_id`;
- 120 событий раньше создания обращения.

После удаления этих нарушений остаётся 144 800 событий.

Порядок очистки:

1. удалить дубли по `event_id`;
2. оставить только события существующих чистых обращений;
3. присоединить `created_at_utc` по `ticket_id`;
4. удалить события, где `event_ts_utc < created_at_utc`;
5. перед JOIN с карточкой агрегировать события до одной строки на `ticket_id`.

## 4. `team_capacity_daily.csv`

Ожидаемая полная сетка:

```text
546 дней × 32 команды = 17 472 строки
```

Контролируемые нарушения:

- 120 отсутствующих комбинаций `date + team_id`;
- 40 повторных комбинаций;
- 16 отрицательных `backlog_start`;
- 24 строки с `active_agents > planned_agents`.

Правила:

- удалить дубли по составному ключу;
- отрицательный backlog заменить на пропуск и восстановить по соседним дням или медиане команды;
- значения `active_agents` выше плана считать ошибочными и ограничить плановым значением только после фиксации нарушения;
- восстановить полную календарную сетку через `MultiIndex.from_product`;
- отдельно пометить восстановленные строки признаком качества.

## 5. Соединения и гранулярность

Перед каждым соединением фиксировать:

- число строк слева и справа;
- уникальность ключей;
- ожидаемую кардинальность;
- число строк после соединения;
- количество неприсоединившихся ключей.

Рекомендуемые проверки:

```python
result = left.merge(
    right,
    on="key",
    how="left",
    validate="many_to_one",
    indicator=True,
)
```

Для событий сначала выполнить `groupby("ticket_id")`, затем соединять результат с обращениями.

## 6. Временной ряд

- даты должны образовывать непрерывный диапазон из 546 дней;
- отсутствующие дни восстанавливаются с нулевым числом обращений;
- обучение и проверка разделяются только по времени;
- случайное перемешивание временного ряда запрещено;
- минимум два baseline: предыдущий день и значение семь дней назад.

## 7. Классификация SLA

До построения модели отделить признаки, доступные в момент прогнозирования, от последующих результатов.

Запрещённые признаки:

- `resolution_min`;
- `first_response_min`;
- `resolved_at_utc`, `closed_at_utc`;
- `csat`, `reopen_count`, итоговые эскалации;
- показатели конца текущего дня;
- будущие события журнала.

Разделение:

- обучение: до 30.04.2026;
- валидация: май 2026;
- финальный тест: июнь 2026.

## 8. Отчёт качества

Минимальные поля отчёта:

| Поле | Назначение |
|---|---|
| `table_name` | Таблица |
| `rule_id` | Идентификатор правила |
| `rule_description` | Описание проверки |
| `failed_rows` | Число нарушений |
| `action` | Исправление или исключение |
| `rows_before` | Строк до шага |
| `rows_after` | Строк после шага |
| `status` | PASS/WARNING/FAIL |
