## 1. Простая бизнес-история

Представим небольшой интернет-магазин.

У нас уже есть таблица `users`. В ней хранятся пользователи:

| id | name | email | age | country | balance |
|---:|---|---|---:|---|---:|
| 1 | Ivan | ivan@example.com | 25 | RUS | 100000.00 |
| 2 | Gleb | gleb@example.com | 26 | RUS | 110000.00 |
| 3 | Sergey | sergey@example.com | 28 | RUS | 90000.00 |
| 4 | Andrew | andrew@example.com | 24 | RUS | 95000.00 |
| 6 | Tom | tom@example.com | 29 | USA | 110000.00 |

Теперь нам нужна таблица заказов `orders`.

Один пользователь может сделать много заказов:

```text
Пользователь Ivan
    -> заказ Product A
    -> заказ Product D

Пользователь Gleb
    -> заказ Product B
    -> заказ Product C
    -> заказ Product E

Пользователь Sergey
    -> заказов пока нет
```

Если хранить всё в одной таблице, данные начнут повторяться. Например, email пользователя будет дублироваться в каждой строке заказа. Поэтому мы разделяем данные:

- `users` — кто покупает;
- `orders` — что покупают;
- `orders.user_id` — ссылка на пользователя из таблицы `users`.

---

## 2. Визуальная схема связи таблиц

```text
users                           orders
+----+--------+                 +----+---------+--------------+
| id | name   |                 | id | user_id | product_name |
+----+--------+                 +----+---------+--------------+
|  1 | Ivan   | <-------------  |  1 |       1 | Product A    |
|  2 | Gleb   | <-------------  |  2 |       2 | Product B    |
|  3 | Sergey |                 |  3 |       2 | Product C    |
+----+--------+                 +----+---------+--------------+
```

Здесь:

- `users.id` — уникальный номер пользователя;
- `orders.user_id` — номер пользователя, который сделал заказ;
- связь строится по правилу: `users.id = orders.user_id`.

Простыми словами:

```text
Если orders.user_id = 2, значит заказ принадлежит пользователю, у которого users.id = 2.
```

## 5. Создать таблицу заказов

```sql
CREATE TABLE orders (
    id INT NOT NULL AUTO_INCREMENT,
    user_id INT NOT NULL,
    product_name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    quantity INT NOT NULL,
    order_date DATE NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Разбор структуры:

| Поле | Тип | Что хранит |
|---|---|---|
| `id` | `INT` | Уникальный номер заказа |
| `user_id` | `INT` | Номер пользователя, который сделал заказ |
| `product_name` | `VARCHAR(100)` | Название товара |
| `price` | `DECIMAL(10, 2)` | Цена одной единицы товара |
| `quantity` | `INT` | Количество товара в заказе |
| `order_date` | `DATE` | Дата заказа |

Разбор ограничений:

| Конструкция | Что означает |
|---|---|
| `PRIMARY KEY (id)` | Поле `id` уникально идентифицирует каждый заказ |
| `FOREIGN KEY (user_id)` | Поле `user_id` является внешним ключом |
| `REFERENCES users(id)` | Значение `user_id` должно существовать в `users.id` |

Простыми словами: база не должна позволить создать заказ для несуществующего пользователя.

---

## 6. Почему цена задана как `DECIMAL`, а не `FLOAT`

В исходном файле поле `price` было задано как `FLOAT`:

```sql
price FLOAT NOT NULL
```

Для учебного примера это может работать, но для денег лучше использовать `DECIMAL(10, 2)`.

Причина простая:

- `FLOAT` — приблизительный тип числа;
- `DECIMAL` — точный тип числа;
- для цен, балансов и финансовых значений лучше использовать точный тип.

В этом файле используем:

```sql
price DECIMAL(10, 2) NOT NULL
```

Это означает: число максимум до 10 цифр, из них 2 цифры после запятой.

Примеры подходящих значений:

```text
10.00
1250.50
99999999.99
```

# Часть 4. Подзапросы

## 17. Что такое подзапрос

Подзапрос — это запрос внутри другого запроса.

Простая логика:

```text
Сначала внутренний запрос находит значение.
Потом внешний запрос использует это значение.
```

Например, задача:

```text
Найти все заказы пользователя Gleb.
```

Можно решить в два шага.

Шаг 1. Найти `id` пользователя Gleb:

```sql
SELECT id
FROM users
WHERE name = 'Gleb';
```

Результат:

```text
+----+
| id |
+----+
|  2 |
+----+
```

Шаг 2. Найти заказы, где `user_id = 2`:

```sql
SELECT *
FROM orders
WHERE user_id = 2;
```

Подзапрос позволяет объединить эти два шага в один.

---

## 18. Найти заказы пользователя через подзапрос

```sql
SELECT *
FROM orders
WHERE user_id = (
    SELECT id
    FROM users
    WHERE name = 'Gleb'
);
```

Как это читается:

```text
Покажи все заказы,
где user_id равен id пользователя,
у которого name = 'Gleb'.
```

Ожидаемый результат:

```text
+----+---------+--------------+-------+----------+------------+
| id | user_id | product_name | price | quantity | order_date |
+----+---------+--------------+-------+----------+------------+
|  2 |       2 | Product B    | 20.00 |        1 | 2023-02-20 |
|  3 |       2 | Product C    | 15.00 |        3 | 2023-02-23 |
|  5 |       2 | Product E    | 25.00 |        1 | 2023-02-26 |
+----+---------+--------------+-------+----------+------------+
```

---

## 19. Важное замечание про подзапрос с `=`

В запросе выше используется знак `=`:

```sql
WHERE user_id = (...)
```

Это означает, что внутренний запрос должен вернуть одно значение.

Если внутренний запрос вернёт несколько строк, MySQL выдаст ошибку.

Например, если в таблице будет несколько пользователей с именем `Ivan`, такой запрос может стать проблемным:

```sql
SELECT *
FROM orders
WHERE user_id = (
    SELECT id
    FROM users
    WHERE name = 'Ivan'
);
```

Поэтому в реальной работе лучше искать по более точному признаку, например по email:

```sql
SELECT *
FROM orders
WHERE user_id = (
    SELECT id
    FROM users
    WHERE email = 'gleb@example.com'
);
```

---

## 20. Подзапрос с `IN`

Если внутренний запрос может вернуть несколько значений, используем `IN`.

Задача:

```text
Найти заказы всех пользователей из страны RUS.
```

Сначала можно найти пользователей из `RUS`:

```sql
SELECT id
FROM users
WHERE country = 'RUS';
```

Потом найти их заказы:

```sql
SELECT *
FROM orders
WHERE user_id IN (
    SELECT id
    FROM users
    WHERE country = 'RUS'
);
```

Разница:

| Оператор | Когда использовать |
|---|---|
| `=` | Когда подзапрос возвращает одно значение |
| `IN` | Когда подзапрос может вернуть несколько значений |

# Часть 5. `UNION`

## 22. Что делает `UNION`

`UNION` объединяет результаты двух или нескольких `SELECT`-запросов в один общий результат.

Важно: `UNION` не склеивает таблицы физически. Он только показывает общий результат запроса.

Простая аналогия:

```text
SELECT 1 дал один список строк.
SELECT 2 дал другой список строк.
UNION показал их вместе.
```

---

## 23. Главное правило `UNION`

У объединяемых запросов должно быть одинаковое количество столбцов.

Например, этот вариант правильный:

```sql
SELECT id, name, 'user' AS source
FROM users
UNION
SELECT id, product_name, 'order' AS source
FROM orders;
```

В обоих запросах три столбца:

| Запрос | Столбец 1 | Столбец 2 | Столбец 3 |
|---|---|---|---|
| Из `users` | `id` | `name` | `'user' AS source` |
| Из `orders` | `id` | `product_name` | `'order' AS source` |

Ожидаемый результат:

```text
+----+-----------+--------+
| id | name      | source |
+----+-----------+--------+
|  1 | Ivan      | user   |
|  2 | Gleb      | user   |
|  3 | Sergey    | user   |
|  4 | Andrew    | user   |
|  6 | Tom       | user   |
|  1 | Product A | order  |
|  2 | Product B | order  |
|  3 | Product C | order  |
|  4 | Product D | order  |
|  5 | Product E | order  |
+----+-----------+--------+
```

Обратите внимание: во втором столбце в результате стоит имя `name`, потому что MySQL берёт названия столбцов из первого `SELECT`.

---

## 24. Более понятный вариант с одинаковыми псевдонимами

Чтобы результат был понятнее, можно явно назвать столбцы:

```sql
SELECT
    id,
    name AS title,
    'user' AS source
FROM users
UNION
SELECT
    id,
    product_name AS title,
    'order' AS source
FROM orders;
```

Теперь второй столбец логически называется `title`: это может быть имя пользователя или название товара.

---

## 25. `UNION` и `UNION ALL`

Есть два похожих варианта:

| Команда | Что делает |
|---|---|
| `UNION` | Объединяет результаты и убирает полные дубликаты строк |
| `UNION ALL` | Объединяет результаты и оставляет все строки, включая дубликаты |

Для обучения можно запомнить так:

```text
UNION — аккуратно объединить без повторов.
UNION ALL — объединить всё как есть.
```

В реальной аналитике `UNION ALL` часто быстрее и прозрачнее, если вы точно знаете, что дубликаты не нужно удалять.

# Часть 6. `INNER JOIN`

## 27. Что такое `JOIN`

`JOIN` нужен, когда данные находятся в разных таблицах, но нам нужен общий результат.

Например, таблица `orders` хранит `user_id`, но не хранит имя пользователя. Чтобы увидеть имя пользователя рядом с заказом, нужно соединить `orders` с `users`.

---

## 28. Простая схема `INNER JOIN`

```text
users.id = orders.user_id
```

```text
users                         orders
+----+------+                 +----+---------+-----------+
| id | name |                 | id | user_id | product   |
+----+------+                 +----+---------+-----------+
|  1 | Ivan | <-------------  |  1 |       1 | Product A |
|  2 | Gleb | <-------------  |  2 |       2 | Product B |
|  3 | Serg |                 |    |         |           |
+----+------+                 +----+---------+-----------+
```

`INNER JOIN` возвращает только те строки, где найдено совпадение в обеих таблицах.

То есть пользователь без заказов в результат не попадёт.

# Часть 7. `LEFT JOIN`

## 33. Что делает `LEFT JOIN`

`LEFT JOIN` возвращает:

- все строки из левой таблицы;
- совпавшие строки из правой таблицы;
- `NULL`, если совпадения справа нет.

Главное правило:

```text
LEFT JOIN сохраняет все строки из таблицы, которая написана слева от LEFT JOIN.
```

---

## 34. Сравнение `INNER JOIN` и `LEFT JOIN`

| Тип соединения | Что возвращает | Простыми словами |
|---|---|---|
| `INNER JOIN` | Только совпавшие строки | Только пользователи, у которых есть заказы |
| `LEFT JOIN` | Все строки из левой таблицы и совпадения справа | Все пользователи, даже если заказов нет |

## 36. Найти пользователей без заказов

Это частая аналитическая задача.

Например:

```text
Найти клиентов, которые зарегистрировались, но ничего не купили.
```

Запрос:

```sql
SELECT
    u.id,
    u.name,
    u.email
FROM users AS u
LEFT JOIN orders AS o
ON u.id = o.user_id
WHERE o.id IS NULL;
```

Как это читается:

```text
Покажи всех пользователей слева,
приклей к ним заказы, если они есть,
а потом оставь только тех,
у кого заказа не нашлось.
```

Ожидаемый результат:

```text
+----+--------+--------------------+
| id | name   | email              |
+----+--------+--------------------+
|  3 | Sergey | sergey@example.com |
|  4 | Andrew | andrew@example.com |
|  6 | Tom    | tom@example.com    |
+----+--------+--------------------+
```

## 37. Важное правило про условия в `LEFT JOIN`

Слушатели часто допускают ошибку: пишут `LEFT JOIN`, а потом условием в `WHERE` случайно превращают его по смыслу в `INNER JOIN`.

Например:

```sql
SELECT
    u.name,
    o.product_name,
    o.order_date
FROM users AS u
LEFT JOIN orders AS o
ON u.id = o.user_id
WHERE o.order_date >= '2023-02-23';
```

Такой запрос уберёт пользователей без заказов, потому что у них `o.order_date` равен `NULL`.

Для начального уровня достаточно запомнить:

```text
Если хотим сохранить пользователей без заказов, аккуратно работаем с условиями по правой таблице.
```

# Часть 8. Простая аналитика по заказам

## 39. Посчитать количество заказов по пользователям

```sql
SELECT
    u.name,
    COUNT(o.id) AS orders_count
FROM users AS u
LEFT JOIN orders AS o
ON u.id = o.user_id
GROUP BY u.id, u.name;
```

Ожидаемый результат:

```text
+--------+--------------+
| name   | orders_count |
+--------+--------------+
| Ivan   |            2 |
| Gleb   |            3 |
| Sergey |            0 |
| Andrew |            0 |
| Tom    |            0 |
+--------+--------------+
```

Почему используется `COUNT(o.id)`, а не `COUNT(*)`:

- `COUNT(*)` считает строки результата после `LEFT JOIN`;
- у пользователя без заказов всё равно будет одна строка с `NULL`;
- `COUNT(o.id)` считает только найденные заказы, потому что `NULL` не считается.

---

## 40. Посчитать сумму заказов по пользователям

```sql
SELECT
    u.name,
    COALESCE(SUM(o.price * o.quantity), 0) AS total_spent
FROM users AS u
LEFT JOIN orders AS o
ON u.id = o.user_id
GROUP BY u.id, u.name;
```

Ожидаемый результат:

```text
+--------+-------------+
| name   | total_spent |
+--------+-------------+
| Ivan   |       44.00 |
| Gleb   |       90.00 |
| Sergey |        0.00 |
| Andrew |        0.00 |
| Tom    |        0.00 |
+--------+-------------+
```

Здесь появляется новая функция `COALESCE`.

Простое объяснение:

```text
COALESCE(значение, 0) означает:
если значение есть — покажи его,
если там NULL — покажи 0.
```

Если у пользователя нет заказов, сумма будет `NULL`. Для отчёта удобнее показать `0`.

---

## 41. Отсортировать пользователей по сумме заказов

```sql
SELECT
    u.name,
    COALESCE(SUM(o.price * o.quantity), 0) AS total_spent
FROM users AS u
LEFT JOIN orders AS o
ON u.id = o.user_id
GROUP BY u.id, u.name
ORDER BY total_spent DESC;
```

Так мы получаем простой рейтинг пользователей по сумме заказов.

# Часть 9. Типичные ошибки новичков

| Ошибка | Почему возникает | Как исправить |
|---|---|---|
| `Cannot add or update a child row` | В `orders.user_id` указали пользователя, которого нет в `users.id` | Проверить пользователя через `SELECT * FROM users;` |
| `Unknown column` | Ошибка в названии столбца | Проверить структуру через `DESCRIBE table_name;` |
| `Table 'orders' already exists` | Таблица уже была создана раньше | Использовать `DROP TABLE IF EXISTS orders;` для учебного повтора |
| Подзапрос с `=` вернул много строк | `=` ждёт одно значение | Использовать более точное условие или оператор `IN` |
| `JOIN` вернул слишком много строк | У пользователя несколько заказов, поэтому строки размножились | Проверить связь один-ко-многим: один пользователь — много заказов |
| Пользователи без заказов пропали | Использовали `INNER JOIN` вместо `LEFT JOIN` | Использовать `LEFT JOIN` |
| Не понимают `NULL` | `NULL` воспринимают как пустую строку или ноль | Объяснить: `NULL` означает отсутствие значения |
| Сумма по пользователю без заказов равна `NULL` | `SUM` по отсутствующим значениям возвращает `NULL` | Использовать `COALESCE(SUM(...), 0)` |
